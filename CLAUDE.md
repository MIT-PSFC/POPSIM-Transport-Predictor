# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Tokamak plasma transport prediction study using POPSIM ML framework. Trains models to predict plasma profiles and power balance on three devices (C-Mod, DIII-D, TCV) with transfer learning between devices. Three active studies: `profile_transfer` (complete, the template for study structure), `power_balance_transfer` (refactored to match it), and `transport_transfer` (time-dependent profile evolution, reuses machinery from both). `trajectory_optimization` is out of scope (briefly attempted March 2026, inconclusive) - do not extend it.

## Architecture

### Data Flow

```
Device sources
    -> datasets/ workflows (per-device, see datasets/dataset_creation.md)
        - C-Mod, MAST: published Zarr stores of transport-validation-datasets (GP-fitted there)
        - DIII-D: disruption-py 0.14 (DISPY EFIT, PTDATA, BOLOM) + IDA profiles, one raw netCDF per shot
        - TCV: DEFUSE h5 exports + LIUQE (MEQ databases) for the rho_pol -> rho_tor_norm map, one raw netCDF per shot
        - One filter spec and one rho_tor_norm map on all four devices, every stored value causal except P_oh and P_rad
        - 1 kHz uniform timebase, profiles on rho_tor_norm
        - Output: Zarr store ds.zarr, IMAS names in SI units
          (dims: shot, time_idx[, rho_tor_norm], time on (shot, time_idx))
    -> organize_data.py
        - get_ds(source, study_type) converts to working units and selects per-study signal prep
        - Concatenate shots, train/val/test split (80/20)
    -> POPSIM module training (submodules/popsim-public/)
        - Input normalization happens INSIDE the modules (see below)
    -> study.py orchestration (cases, W&B sweeps, SLURM)
    -> analysis / plotting
```

### Key Abstractions

**Study/Case pattern** (`orchestration/study.py`): A `Study` holds many `Case` objects. Each case is a unique combination of case-grid axes (e.g. `model_type x training_data x normalization x domain_adaptation x freeze x num_target_shots`). Cases support prerequisites (chained dependencies, e.g. transfer cases depend on their pretrained checkpoint case; the power balance sciml-taue-nn/sciml-taue-scalinglaw model types depend on p_oh/p_rad submodule cases). `ProfileStudy` (`profile_transfer/profile_study.py`) is the reference implementation; `PowerBalanceStudy` (`power_balance_transfer/power_balance_study.py`) and `TransportStudy` (`transport_transfer/transport_transfer_study.py`) mirror it. TransportStudy's sciml prereq chain is two deep: sciml -> power_balance + profile pseudo-model-type cases (trained with the OTHER studies' TRBs and study types, variants picked by the `power_balance_model_type` / `profile_model_type` config fields), and power_balance -> p_oh + p_rad.

The `Study` base provides everything generic; subclasses only declare what differs:

- Base `Study.Case` (dataclass): common fields (`model_type`, `training_data`, `domain_adaptation`, `num_target_shots`, `prereqs`), validation, prereq building (`[hyperparam case, _model_type_prereqs(), transfer pretrain case]` deduped in order), `replace` (rebuild through the real constructor), hyperparam-case logic driven by `HYPERPARAM_FIELDS` (each maps to a `config.hyperparam_<name>` attribute), token-driven `__str__` (`case.{mt}.td_{td}` + `STR_TOKEN_FIELDS` tokens + `targ_{n}` when da or exnihilo + `da_{da}`), and `__hash__` (all fields except prereqs).
- Subclass `Case` is thin: extra fields (`data_normalization`, `freeze_shapes` for profile; `data_normalization`, `freeze_submodules` for power balance; `freeze_submodules`, `geometry_builder`, `torax_state` for transport), the three ClassVars (`VALID_MODEL_TYPES`, `STR_TOKEN_FIELDS`, `HYPERPARAM_FIELDS`), and an `__init__` that sets the extra fields then calls `_init_common`. TWO DATACLASS TRAPS: the subclass body must keep its own `__init__` (or `@dataclass` regenerates one, silently dropping validation and prereq building) and must alias `__hash__ = Study.Case.__hash__` (or `@dataclass` with eq=True sets `__hash__ = None`).
- `make_train_config` is a template method: base builds the shared scaffold (dataloader/loss/optimizer bases, weighted `device_weights` injected into the loss config which the val suite aliases, transfer checkpoint wiring via `_set_transfer_checkpoint`, tuned-config merge, then `_scale_transfer_lr` AFTER the merge so swept configs cannot overwrite it). Subclass hooks: `_base_dataloader_config(case)`, `_base_loss_config()`, `_base_optimizer_config()` (profile overrides to add grad clipping), `_model_train_spec(case, dataloader_config_base) -> ModelTrainSpec` (per-model-type train_run_builder + dataloader + model_init dicts), `_tuned_model_init_updates(case, tuned_config)`. Tuned-config merge semantics are deliberate: `TUNED_DATALOADER_KEYS` are indexed strictly (KeyError if missing), `TUNED_LOSS_KEYS` use `.get` fallback because tuned configs on disk may lack them; the optimizer_config is replaced wholesale. Power balance's `_make_submodule_config` recurses through `make_train_config`, so p_oh/p_rad submodule configs get their own tuned merge and transfer wiring.
- `run_study` is a base classmethod (Fire CLI reads its signature, so flags live in one place): config TOML parse via `cls.Config`, `setup_directories`, partition check, `_visualize_data()` (uses the `DATA_VISUALIZATION` ClassVar), orchestration loop + `collect_results` + write `collected_results.nc` (skipped if it exists), then `_run_analysis(enable_parallelism)`. Each study module keeps `run_study = <StudyClass>.run_study` at module level for the `fire.Fire` main and test imports.
- `collect_results` schemas intentionally differ: the base implementation emits the per-case scalar summary (dims: case_idx) via `_summarize_case_errors`, which power balance and transport both inherit unchanged; profile overrides it with a per-shot long-form dataset (dims: record). All use the base `case_coords` driven by `_CASE_COORD_NAMES`.
- `_run_analysis` follows the same shape in both studies: with parallelism, per-case analysis (stage metrics + case report) fans out as one SLURM CPU job per case via `orchestration/case_analysis.run_case_analysis_parallel(study)`. The per-study pieces are declared as ClassVars `ANALYSIS_METRICS_MODULE` / `ANALYSIS_REPORTS_MODULE` (dotted paths; the metrics module exports `compute_and_save_case_metrics`, the reports module `generate_case_report` + `analysis_case_done`), which the driver and `slurm_utils.launch_case_analysis_parallel` resolve. Then the driver runs `collect_metrics` (per-case `case_metrics.nc` caches combined into `collected_metrics.nc`, stages from `orchestration/stages.segment_stages`), comparison figures, serial-fallback case reports, and per-axis comparison tables (both studies: each study's tables.py declares a ComparisonTableSpec plus its per-case stats frame, the shared grouping/markdown/csv writer lives in orchestration/tables.py). Power balance per-shot errors in result files are raw time integrals (long shots score worse); its study_metrics/case_reports rank shots by TIME-AVERAGED error instead.
- Other subclass ClassVars: `SWEEP_CONFIG_DIR`, `STUDY_TYPE`, `DATA_VISUALIZATION`, `CASE_AXIS_FIELDS` (config axis names logged at init).

CRITICAL: `str(case)` names checkpoint dirs, result files, tuned-config paths, wandb projects, and SLURM job names - byte-level drift orphans existing runs. `restore_predictor.checkpoint_to_profile_case` parses case-directory names back into Cases and must stay in sync with `__str__`. Each study's `tests/<study>/test_*_case_naming.py` pins the literal case strings.

**TRB pattern and shared helpers** (`modules/trb_utils.py`, `modules/power_balance/scalar_power_trb.py`): TrainRunBuilders share `trapezoid_dropna` / `integrate_error_over_time` (per-shot NaN-safe time integrals of error), `make_exponential_adamw` (the standard optimizer), `make_loss_eval_suite` (validation loss mean + a <=100-point subsampled loss vector for wandb; creates a fresh jitted closure per suite so eqx.filter_jit caches never collide across cases), `resolve_case_datasets` (per-case dataset selection and prep shared by EVERY study TRB, incl. the transfer_pretrain normalizer-fit dataset passed via `train_dl.normalizer_fit_ds`), and `get_time_dep_dataloaders` + `mask_to_largest_contiguous_segment` (the segment-based time-dependent dataloader construction on top of it, parameterized only by study_type; the power balance and transport TRBs both delegate to it, the profile TRB builds its time-independent dataloaders on `resolve_case_datasets` directly). `ScalarPowerTRB` is the shared base for the p_oh/p_rad predictors - `OhmicPowerTRB` / `RadiatedPowerTRB` are subclasses that only set `SIGNAL` and `MODULE_CLS` ClassVars; sweep configs reference them by their original dotted paths. `TransportPredictorTRB` reuses `ProfilePredictorTRB.get_test_eval_suite` as-is (its study_results handles the time-dep dim suffixing and emits the per-channel and combined error variables), and the transport analysis modules (`transport_transfer/study_metrics.py`) re-export the power balance stage-metric machinery wholesale.

**DataWorkflow** (`datasets/workflow.py`): Abstract base for device-specific data acquisition. Each device (cmod/, d3d/, tcv/, mast/) implements this interface and outputs xarray Datasets in a standardized schema. The base provides `standardize_dim_names` (rename to POPSIM's `shot`/`time_idx`/`time` conventions), `has_all_nan_signal` (raw-stage skip-shot check), and a default `device_specific_culling` (cull when either profile is all NaN, d3d extends it with its excluded shots). `RawFileWorkflow.filter_ds` and `cull_shot` apply the one filter spec every device store shares, imported from transport-validation-datasets `filters.py` (`slice_filter_mask`, `radiated_fraction_reason`, `energy_sanity_reason`, `clip_powers`): the end of the shot (last |ip| above its `min_filter` threshold, minus `end_margin_s`), every `DATASET_0D_SIGNALS` finite, `min_filter` / `max_filter` thresholds on the raw samples (`greenwald_fraction` derived for the max filter), and `transient_filter` thresholds on a centered 5 ms boxcar each cut a gap, every failed time also cuts the 20 ms before it (`FAILURE_MARGIN`, the smoothed powers lead the events), and only the longest contiguous segment is kept. The culls (`min_pulse_length_s`, `min_radiated_fraction`, energy sanity, `density_ratio_bounds`) run on every device, with per-device thresholds as ClassVars of the device workflow. `RawFileWorkflow.load_shot` filters, clips and culls, and plots each shot's unfiltered 0D signals once with transport-validation-datasets `plot_unprocessed_data` into `accepted_shots/` (kept segment green) or `rejected_shots/` under the dataset dir, transients red, as tvd does for C-Mod and MAST. Every stored value is causal except `power_ohm` and `power_radiated`: 0D signals are never interpolated (transport-validation-datasets `signal_on_grid` averages a faster-than-grid signal over each grid step and holds a slower one forward), and derivatives are backward differences. The two powers are noise-dominated at 1 kHz, so every device stores them centered-smoothed: DIII-D's at the source (EFIT `poh` takes +-100 ms slopes, `\bolom::prad_tot` a 50 ms boxcar applied twice), TCV `PradTot` as DEFUSE gives it, and the rest with that same 50 ms kernel (`smoothed_power`). The logic every device shares (the 1 kHz timebase, `signal_on_grid`, the rho_tor_norm map, the 0D helpers) is imported from transport-validation-datasets `machine/generic.py`, never copied.

Two kinds of device workflow: `PublishedStoreWorkflow` (C-Mod, MAST) builds the stores from a transport-validation-datasets published Zarr store, and `RawFileWorkflow` (TCV, DIII-D) first pulls one raw netCDF per shot (`--mode raw`) and then processes them (`--mode process`). The `SIGNAL_ATTRS` / `STORE_ATTRS` ClassVars are applied to every stored shot in `process_fn`, and DIII-D and TCV use them to give every variable a description, units, and its IMAS path (`ref`). Both raw-file devices store the full schema, profile companions included, and hold each usable profile slice onto the 1 kHz timebase for a capped number of median slice steps with transport-validation-datasets `hold_onto_grid`, which also gives `fresh_profile`. A slice that does not map or lacks a fit is dropped before the hold, so the slice before it holds over it, as in transport-validation-datasets. DIII-D (`datasets/d3d/`) pulls through PyPI disruption-py 0.14.0 in the main venv: `[tool.uv] override-dependencies` lifts its numpy<2 pin, and since the OMEGA MDSplus cannot import under numpy 2, disruption-py falls back to the mdsthin thin client by itself. Every EFIT signal, P_oh (`poh`) included, comes from the shot's `DISPY` runtag run (`DispyEfitNicknameSetting`, strict, no efit01 fallback) through custom physics methods only (the built-ins interpolate), P_rad is the bolometer total `\bolom::prad_tot`, and the IDA Te/ne profiles (on psi_n) are mapped onto rho_tor_norm through the DISPY q profile. The IDA databases are a priority list in `d3d/config.toml` (`IdaDatabase`, optionally limited to a shotlist), and both stores carry `ida_source`, a JSON map from each stored shot to its IDA folder. TCV (`datasets/tcv/`) reads the DEFUSE h5 exports directly with h5py. P_rad is DEFUSE `PradTot` (total, like DIII-D and MAST), P_oh is computed from `I_P`, `Vloop` (sign flipped onto I_P's), `LI` and the geometric major radius `R_geom`, and b0 is `BZERO` at LIUQE's r0 = 0.88 m. The DEFUSE Te/ne fits are on rho_pol = sqrt(psi_N), NOT rho_tor_norm, and are mapped through the q profile of LIUQE from the MEQ databases (the analytic log-q tail of `phi_n_map` covers the diverging q at the LCFS, LIUQE's FtPQ is quantized and unused), so only the 964 shots with a MEQ database (60001-82878) are built. DEFUSE gives no uncertainty, so the TCV error companions are the 0 sentinel. Details in `datasets/dataset_creation.md`.

**Input normalization as POPSIM modules** (`modules/normalization.py`): the power-balance models take the same 7 physical inputs (`ip_MA, b_geo, geometric_axis_r, minor_radius, elongation, n_e_line_average_1e20, power_additional_MW`) plus `ds_source_idx`. Each model owns an `InputNormalizer` (`raw` identity / `physics` dimensionless / `zscore` per-device / `coral` per-device covariance alignment / `physics-coral` and `physics-zscore` stat stages fitted in the physics feature space), fitted from TRAINING data only at model_init and stored as frozen buffers (they checkpoint with the model but are never trainable - trainable selectors pick `module.nn` leaves explicitly). The profile and transport studies' counterparts are `profile_predictor/module.make_nn_input_normalizer` (10 dimensionless `nn_inputs`) and `transport_predictor/module.make_transport_nn_input_normalizer` (those 10 slots from the measured Wtot plus `paux_norm`), thin wrappers over the shared `normalization.make_feature_normalizer` + `feature_fit_arrays` which hold the one method dispatch (`physics` identity / `physics-coral` / `physics-zscore`, `FEATURE_NORMALIZATIONS`); same contract as `make_normalizer` - fit dataset `None` yields identity buffers with the checkpoint's pytree structure. All three studies' TRBs pick the fit dataset the same way (`getattr(train_dl, "normalizer_fit_ds", train_dl.ds)`, skipped entirely when a transfer checkpoint will overwrite the buffers) and index `data_normalization` strictly. `organize_data.normalize_domain` implements the same math on whole datasets for data visualization only, with `feature_space` selecting which family's features the physics* methods run on (`power_balance` = the 7 `physics_feature_vec` slots, `profile` = the 10 `nn_inputs`, `transport` = the 11 transport features).

**Data visualization** (`orchestration/data_visualization.py`): `DataVisualizationBase` holds the shared hazard-extrapolation and domain-overlap plotting; each study's `data_visualization.py` is a thin subclass setting `STUDY_TYPE`, `VAR_GROUPS` (variable pairs per normalization method), and `FEATURE_SPACE` when its models do not consume the power-balance inputs (profile_transfer sets `"profile"`, transport_transfer `"transport"`, so their physics* plots show the features those modules actually normalize). Shared dark-theme figure styling (colors, `style_axis`) lives in `transport_study/plot_style.py`.

**Module pattern**: Predictors inherit from POPSIM's `TimeIndepModule`/`TimeDepModule`. Profile predictor (time-indep) predicts Te/ne on a uniform 51-point `rho` grid over `[0, 1]` (not psi_n); model families: `shape_init_pca` / `shape_init_kmeans` (B-spline shape bases weighted by an NN, shapes optionally frozen), `unstructured_nn`, `reservoir`, and `torax-constant` / `torax-cgm` / `torax-gyrobohm` / `torax-qlknn` (differentiable TORAX simulation with NN-predicted transport/edge/source parameters). torax-* model types additionally carry a `geometry_builder` case axis (`circular` or `miller`, see `torax_module.build_circular_geometry_jax` / `build_miller_geometry_jax`); no default is suppressed from `str(case)` for this axis (every case gets an explicit `geom_` token), and it is deliberately NOT a `HYPERPARAM_FIELDS` entry so `miller` cases get their own hyperparameter sweep and tuned config instead of inheriting circular's. Power balance (time-dep, simple-Euler stepper, `energy_mhd_MJ` state) predicts stored-energy evolution with four architectures: `sciml-taue-scalinglaw` (H89/H98 tau_e blend gated by a P_LH scaling; consumes PHYSICAL units; called `scaling_law` before July 2026), `sciml-taue-nn` (bounded NN tau_e, physics power balance dW/dt = P_aux + P_oh - P_rad - Wtot/tau_e; called `sciml` before July 2026), `mlp` (MLP directly predicts dW/dt; called `unstructured_nn` before July 2026 - the PROFILE study still uses that name for its own MLP family), and `transformer` (recurrent causal attention: a rolling buffer of the past PREDICTED Wtot values is carried in the module State as a discrete `discrete_no_save_field`, seeded with the measured t0 Wtot tiled; the embedded-input query attends over embedded Wtot tokens plus a learned per-slot position embedding, needed because scalar tokens are otherwise permutation-invariant - see `popsim/modules/delay.py` for the discrete-state pattern). `sciml-taue-scalinglaw` and `sciml-taue-nn` hold `p_oh` / `p_rad` submodule predictors trained as their own prereq cases and restored from checkpoints; during joint training the loss anchors the submodule predictions to the measured `power_ohm_MW` / `power_radiated_MW` targets (`anchor_weight_p_oh` / `anchor_weight_p_rad` loss keys, training loss only so `val/loss.mean` stays pure Wtot, no-op for model types whose target_vars lack the powers) and the optimizer runs the submodules at a reduced learning rate (`submodule_lr_factors` in the power balance `_base_optimizer_config`, default 0.1x, applied by pytree-path labeling in `trb_utils.make_grouped_exponential_adamw` via optax multi_transform). Transport predictor (time-dep, simple-Euler stepper, `modules/transport_predictor/`) predicts ne/te profile EVOLUTION on the same rho grid from the power-balance inputs plus triangularities (no measured betan - beta quantities derive from the evolving state Wtot): `transformer` (rolling profile-history buffer as discrete state, same shape as the power balance transformer: current-feature query attends over position-embedded profile tokens - only predicted profiles are kept as history, never past input features), `sciml` (composes a trained PowerBalance for the Wtot state and a trained ProfilePredictor fed the state-implied betan; its Output surfaces `energy_mhd_MJ_pred` / `power_ohm_MW_pred` / `power_radiated_MW_pred` so the training loss can anchor them to the measured signals - `anchor_weight_wtot` / `anchor_weight_p_oh` / `anchor_weight_p_rad` loss keys, training loss only, no-op for the other model types whose target_vars lack the signals - and the optimizer runs the whole power_balance subtree at a reduced learning rate via `submodule_lr_factors` while the profile predictor keeps the full schedule, same `make_grouped_exponential_adamw` mechanism as the power balance study), and `torax-*` (one TORAX solver step of the 1 ms dataset timebase per call, config from `transport_predictor/train_configs.make_transport_torax_config`). Unlike the profile study's TORAX modules, which infer the heating magnitude with an NN, the transport ones feed the MEASURED `power_additional_MW` straight to `sources.generic_heat.P_total` and let the sources network predict only the deposition shape, the gas-puff fueling, and `absorption_fraction = 1 - exp(-n_e_line_average_1e20 * softplus(nn))` - a Beer-Lambert shine-through form that is always in (0, 1) and never gradient-dead at saturation. The profile modules keep the fixed config absorption of 0.9, where it would be degenerate with their NN-predicted `P_total`. torax-* carry both the `geometry_builder` axis and a `torax_state` axis ("rebuild" re-seeds TORAX from stored ne/te each step, "carry" keeps the full ToraxSimState); in this study (unlike profile_transfer) both axes' defaults ("circular", "rebuild") are suppressed from `str(case)`, and neither is a `HYPERPARAM_FIELDS` entry. Normalization is not a case axis in the transport study (unlike profile, where it is): a study-wide `data_normalization` config field ("physics", "physics-coral", or "physics-zscore") controls the per-device stat stage (`CoralFeatureNormalizer` / `ZScoreFeatureNormalizer`) over the 11 transport features. `TransportPredictorEnv` (in module.py) seeds each architecture's state from the measured t0 signals carried in the dataloader's state_vars.

**Profile loss split** (`profile_predictor/trb.py`, mirrored in `transport_predictor/trb.py`): both studies build their training and validation losses from one builder with a `use_huber` switch, and the two halves must stay different. Training uses the swept `huber_delta` on the raw residual and never reads the error bars. Validation is delta-free absolute error with the residual inside the GP-fit error bar down-weighted by `within_error_weight`, so the sweep metric `val/loss.mean` cannot be gamed by shrinking delta and checkpoint selection does not chase fit noise the measurement cannot resolve. `within_error_weight` is read STRICTLY from the loss config (a silent default would change checkpoint selection without changing the case); every study sets it in `_base_loss_config`, and `profile_transfer/study_metrics.py` reimplements the same softening in numpy for scoring, reading the same key off `make_train_config`. The transport loss adds a freshness mask on top: the profile terms are multiplied by the `fresh_profile` target var so forward-filled timeslices steer neither training nor checkpoint selection, while the anchor terms stay unmasked because their measured signals exist at every timeslice.

**Domain adaptation / transfer modes** (`domain_adaptation`): `none` (train and test on the same device(s), baseline and hyperparam case), `weighted` (add a small amount of highly-weighted target data during training, weights from `Study._make_weighted_device_weights`; this was called `mixing` before July 2026, so old run artifacts may carry the name), `addition` (add target shots to the training set as normal samples, no weighting - identical datasets to `weighted`, differs only in the absence of `device_weights`), `transfer` (pretrain on source with da=none and num_target_shots=0, restore checkpoint, fine-tune last layers on target with lr scaled by `TRANSFER_LR_FACTOR`). The `exnihilo` training-data option trains from scratch on the target device only. The test set is the held-out highest-hazard target shots (hazard = per-shot p95 of normalized (energy_mhd_MJ^2 + ip_MA^2)^0.5, called "performance" before July 2026); domain-adaptation cases reuse that test set for checkpoint selection (no separate val set, slightly optimistic but consistent).

### Config

- `transport_study/config.py`: `StudyConfig` (Pydantic, frozen, global one-shot proxy `config`), reads `PTPS_*` env vars
- `orchestration/study.py`: `CaseGridConfig(StudyConfig)` shared base for study configs (training_datasets, domain_adaptation_methods, target_test_set_size, hyperparam_domain_adaptation, hyperparam_num_target_shots, dataset_fractions, from_toml/save) plus the shared `is_compatible` config-lock check, which compares study identity and the hyperparam fields listed in the per-study `COMPAT_HYPERPARAM_FIELDS` ClassVar (case-grid axes like model_types may differ between runs); each study nests its own `Config(CaseGridConfig)` adding model_types and its study-specific hyperparam fields. `HYPERPARAM_TARGET_SHOTS` also lives in study.py (power_balance_study re-exports it)
- Per-device `config.toml` files in each dataset subfolder
- `pyproject.toml`: dependencies, build (hatchling), tooling config. popsim, torax and transport-validation-datasets install editable from their submodules (`[tool.uv.sources]`), so a clone needs `git submodule update --init` before `uv sync`. disruption-py is pinned to the PyPI 0.14.0, and `[tool.uv] override-dependencies` sets numpy to popsim's range over disruption-py's numpy<2 pin
- GPU group: `uv sync --group gpu` for JAX CUDA 13 support

### Data Schema

Every device store holds the shared schema of transport-validation-datasets (`store_schema.STORE_SIGNAL_ATTRS`, every signal with its unit and IMAS ref), IMAS names in SI units on `(shot, time_idx[, rho_tor_norm])` with `time` on `(shot, time_idx)`: `ip`, `b0`, `energy_mhd`, `beta_tor_norm`, `n_e_line_average`, `minor_radius`, `geometric_axis_r`, `elongation`, `triangularity_upper` / `_lower`, `power_ohm`, `power_radiated`, the heating powers `power_nbi` / `power_ic` / `power_lh` / `power_ec`, `r0` on `(shot,)` (the fixed major radius b0 is given at, as IMAS defines b0), the profiles `t_e` / `n_e` with `_error`, `_gradient`, and `_gradient_error` companions, `fresh_profile`, and `fresh_equilibrium` (1 where a usable reconstruction lands, the equilibrium signals hold for at least 10 ms over the rest). `get_ds` converts a store to the study's working units with `signals.convert_to_working_units`: any non-SI unit becomes a name suffix (`ip_MA`, `energy_mhd_MJ`, `n_e_line_average_1e20`, `power_ohm_MW`, `t_e_keV`, `n_e_1e20`, ...) the four heating powers sum to `power_additional_MW`, and `b_geo = b0 r0 / geometric_axis_r` is the vacuum field at the geometric axis, which every model uses (TORAX `B_0` at `R_major`, q_star, aB0, beta_N, the H89 / H98 / P_LH scalings). Power balance inputs are `ip_MA`, `b_geo`, `geometric_axis_r`, `minor_radius`, `elongation`, `n_e_line_average_1e20`, `power_additional_MW`, with `energy_mhd_MJ` the target. The profile and transport preps interpolate the profiles onto the uniform 51-point `RHO_GRID` over `[0, 1]` and add `t_e_shape` / `n_e_shape`. The profile prep keeps only `fresh_profile == 1` slices, the transport prep is the union of both studies' signals minus `beta_tor_norm`, keeps the forward-filled profile timeslices (contiguous segments matter more than freshness for rollouts, `fresh_profile` rides along as data), and reindexes to the uniform timebase.

### Tests

`uv run pytest` runs the fast suite only: `addopts = -m 'not slow'` in pyproject. The `slow` marker covers anything that trains a model, runs a TORAX relaxation, renders comparison figures, or needs real device data (the DIII-D data servers and IDA database, for the live D3D shot test). Run those with `-m slow` on a GPU node, one suite at a time - concurrent suites OOM the node GPU. Study tests also need the `PTPS_*` env vars from `.vscode/launch.json`; without them they fail with misleading shot-count errors.

On a node without a GPU (like the interactive node), the jax CUDA13 plugin's CUDA library version check hangs forever at the first JAX op, which `popsim.ml` runs at import, so collection never finishes and pytest prints nothing. The root `conftest.py` defaults `JAX_PLATFORMS=cpu` when no `/dev/nvidia*` device exists, which also covers VSCode test discovery. Any other entry point that imports JAX on such a node still needs `JAX_PLATFORMS=cpu` set by hand.

The sample device datasets (`cmod-low1/low2/high.nc`, `mast-low1/low2/high.nc`) are NOT in the repo (they were Git LFS files until September 2026). Tests that open them read them from the directory in `PTPS_TEST_SAMPLE_DIR` via `tests/sample_data.SAMPLE_DIR` and carry `requires_sample_data`, which skips them when the variable is unset. Tests that only need a loaded config use `path/to/...` placeholders, and study tests that only build configs use a `tmp_path` working dir so no stale `config_lock.toml` can trip them.

Organization rules the suite follows:

- Tests mirror the package layout. Cross-study behavior is tested once in `tests/orchestration/`, not once per study: `test_study_config.py` (config-lock and TOML round trip, parametrized over all three studies), `test_sweep_configs.py` (every sweep yaml of every study, driven off `Case.VALID_MODEL_TYPES`), `test_tables.py` (the generic comparison-table writer), `test_stages.py` (stage segmentation). Per-study files cover only what actually differs - case naming, the case grid, per-study table specs and plotting. Architecture-level module behavior lives under `tests/modules/<family>/`: `tests/modules/transport_predictor/test_transport_module.py` covers env state seeding, trainable selections, the transformer history buffer, and the TORAX P_aux / absorption wiring, while `tests/transport_transfer/` keeps only study-level wiring.
- Never let a test reach into an underscore-prefixed production name. When coverage needs an internal, the fix is to make the symbol public (that is why `case_coords`, `replace`, `kill_stuck_jobs`, `make_weighted_device_weights`, `stage_shots`, `nn_coefficients`, `build_provider_and_geo` and `transport_coefficients` carry no underscore) or to drive it through its public caller (`_summarize_case_errors` via `collect_results`, `_kill_long_pending_jobs` via `run_unfinished_cases`).
- Orchestration tests drive `StubStudy`/`StubCase` from `tests/stubs.py` via the `make_stub_study` fixture rather than building a real case grid. `stubs.py` doubles as the ANALYSIS_REPORTS_MODULE for the parallel-analysis driver test.
- `tests/modules/profile_predictor/conftest.py` provides `make_torax_module` and `sample_timeslices`; TORAX-backed tests must use them instead of re-deriving module kwargs (the sample files predate `ds_source_idx`, which the fixture fills in). Tests using `sample_timeslices` must carry `requires_sample_data`.
- Test modules never import an underscore-prefixed name from the package. When a test needs to reach production internals, either the symbol is public or the test goes through the public path.
- No docstring-only stub bodies remain: every test in the suite is implemented. New stubs may still be written to mark coverage to be filled in by hand, but they are a temporary state, not the resting one.
- `tests/modules/profile_predictor/test_miller_geometry.py::test_miller_circular_limit_metrics_small_epsilon` fails at HEAD for reasons outside the package (g2 tolerance, 4.6 percent vs the 2 percent bound).
