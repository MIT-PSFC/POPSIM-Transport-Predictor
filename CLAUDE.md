# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Tokamak plasma transport prediction study using POPSIM ML framework. Trains models to predict plasma profiles and power balance on four devices (C-Mod, MAST, DIII-D, TCV) with transfer learning between devices. Three active studies: `profile_transfer` (complete, the template for study structure), `power_balance_transfer` (refactored to match it), and `transport_transfer` (time-dependent profile evolution, reuses machinery from both). `trajectory_optimization` is out of scope (briefly attempted March 2026, inconclusive) - do not extend it.

## Architecture

### Data Flow

```
Device sources
    -> transport-validation-datasets (submodule, builds every device, see its README)
        - C-Mod, MAST: GP fit Thomson (zk), up to <ds>_published.zarr
        - TCV: DEFUSE 0D + raw Thomson, LIUQE GEQDSK, GP fit (zk), up to <ds>_internal.zarr only
        - DIII-D: disruption-py (DISPY EFIT 0D + GEQDSK), IDA GP fits carried over (ida), up to <ds>_internal.zarr only
        - One filter spec and one rho_tor_norm map on all four devices, every stored value causal except the smoothed P_oh and P_rad,
          the TCV n_e fringe-jump correction, and the EFIT and Thomson slices snapped to the nearest grid time (up to 0.5 ms early)
        - power_ohm = Ip V_loop - dW_pol/dt from the GEQDSK block alone on every device (DataWorkflow.add_ohmic_power):
          V_loop = sigma_Bp 2 pi dpsi_boundary/dt at the LCFS, W_pol the psirz integral, no measured flux loop
        - 1 kHz uniform timebase, profiles on rho_tor_norm, IMAS names in SI units
    -> datasets/ wrappers (see datasets/dataset_creation.md)
        - StoreWorkflow selects the study signals of a TVD store into ds.zarr
          (dims: shot, time_idx[, rho_tor_norm], time on (shot, time_idx))
    -> organize_data.py
        - get_ds(source, study_type) converts to working units, adds the hazard metric and runs the per-study prep
        - Per source device a hazard-sorted 80/20 train/val split (the top-hazard fifth is val),
          the target test set and training shots come from target_shots.py (see Domain adaptation below)
        - The training data stays a list of parts (each source's train then val shots, then the target's training shots),
          merged only where it is small (merge_parts: val sets, 0D, the compacted profile view)
    -> trb_utils.segmented_train_dataloader (time-dependent studies)
        - popsim segments each part alone and the segments are merged back into popsim's order,
          so no shot is NaN-padded to another device's length (a DIII-D shot is 20x a MAST one).
          The data is loaded eagerly, so the padding was resident memory (57.5 GB peak in the hs1 debug smoke before the change).
          A room-keeper episode per part reproduces the merged run's tail windows exactly
          (tests/modules/test_segmented_dataloader.py asserts identical samples, order and shuffled batches)
    -> POPSIM module training (submodules/popsim-public/)
        - Input normalization happens INSIDE the modules (see below)
    -> study.py orchestration (cases, W&B sweeps, SLURM)
    -> analysis / plotting
```

### Key Abstractions

**Study/Case pattern** (`orchestration/study.py`): A `Study` holds many `Case` objects. Each case is a unique combination of case-grid axes (e.g. `model_type x training_data x normalization x domain_adaptation x freeze x num_target_shots`). Cases support prerequisites (chained dependencies, e.g. a transfer case depends on its transfer_pretrain twin, and the power balance sciml-taue-nn / sciml-taue-scalinglaw model types depend on p_oh / p_rad submodule cases). `ProfileStudy` (`profile_transfer/profile_study.py`) is the reference implementation, `PowerBalanceStudy` (`power_balance_transfer/power_balance_study.py`) and `TransportStudy` (`transport_transfer/transport_transfer_study.py`) mirror it. TransportStudy's sciml prereq chain is two deep: sciml -> power_balance + profile pseudo-model-type cases (trained with the OTHER studies' TRBs and study types, variants picked by the `power_balance_model_type` / `profile_model_type` config fields), and power_balance -> p_oh + p_rad.

The `Study` base provides everything generic, subclasses only declare what differs:

- Base `Study.Case` (dataclass): common fields (`model_type`, `training_data`, `domain_adaptation`, `num_target_shots` (>= 0), `target_shot_order`, `model_size`, `prereqs`), validation, prereq building (`[hyperparam case, model_type_prereqs(), transfer pretrain case]` deduped in order), `replace` (rebuild through the real constructor), hyperparam-case logic driven by `HYPERPARAM_FIELDS` (each maps to a `config.hyperparam_<name>` attribute), token-driven `__str__` (`case.{mt}.td_{td}` + `STR_TOKEN_FIELDS` tokens + `size_{s}` unless the base `sweep` size + `targ_{n}` when da or exnihilo + `order_{o}` unless the base ascending order + `da_{da}`, the freeze tokens of all three studies suppressed at False so only frozen cases carry `freeze_True`, likewise the `mo_` token of power balance and transport so only multiobjective cases carry `mo_True`), and `__hash__` (all fields except prereqs).
- Subclass `Case` is thin: extra fields (`data_normalization` and `freeze_shapes` for profile, `data_normalization`, `freeze_submodules` and `multiobjective` for power balance, `freeze_submodules`, `geometry_builder`, `torax_state` and `multiobjective` for transport), the three ClassVars (`VALID_MODEL_TYPES`, `STR_TOKEN_FIELDS`, `HYPERPARAM_FIELDS`), `normalization_method()` (the method the case trains with, which decides its transfer twin), `pin_inapplicable_axes(fields)` (calls the base, which pins the target shot order to ascending at 0 target shots, then pins the axes a model type ignores, freeze to the hyperparam_freeze_* value, multiobjective to hyperparam_multiobjective outside each study's `MULTIOBJECTIVE_MODEL_TYPES` and geometry / torax_state to circular / rebuild), and an `__init__` that sets the extra fields then calls `init_common`. TWO DATACLASS TRAPS: the subclass body must keep its own `__init__` (or `@dataclass` regenerates one, silently dropping validation and prereq building) and must alias `__hash__ = Study.Case.__hash__` (or `@dataclass` with eq=True sets `__hash__ = None`).
- `make_train_config` is a template method: base builds the shared scaffold (dataloader/loss/optimizer bases, the weighted `device_weights` and the per-device `chi_sigma_floors` injected into the loss config, which the val suite aliases, the training losses' statistics of the case's own training shots (`Study.training_loss_statistics`: `residual_scales` and `train_chi_sigma_floors`, cached per training-data selection, never the held-out or test shots) and the anchor terms' `anchor_huber_deltas` (`Study.anchor_huber_deltas`, the tuned `huber_delta` of the study's hyperparam case of the model type predicting each anchored signal, `ANCHOR_DELTA_MODEL_TYPES`, a missing tuned config raises), transfer checkpoint wiring via `_set_transfer_checkpoint`, tuned-config merge, then `_scale_transfer_lr` AFTER the merge so swept configs cannot overwrite it). Subclass hooks: `base_dataloader_config(case)` (spreads the base `target_split_config(case)`: training data, da and the `TargetSplit` fields), `base_loss_config(case)` (transport returns the power balance study's `POWER_BALANCE_LOSS_DEFAULTS` for its p_oh / p_rad / power_balance pseudo-types), `base_optimizer_config()` (power balance and transport add `submodule_lr_factors`, popsim's Trainer clips every gradient at global norm 0.5), `model_train_spec(case, dataloader_config_base) -> ModelTrainSpec` (per-model-type train_run_builder + dataloader + model_init dicts). The tuned-config merge (`_apply_tuned_config`) replaces the optimizer_config wholesale, indexes `TUNED_LOSS_KEYS` strictly (KeyError when a tuned config lacks one, a loss key only where the case's own base loss config holds it) and copies the model_init keys the model type's sweep yaml varies (`Study.tuned_model_init_updates` over `sweep_model_init_parameters`, so no study lists them by hand), while the dataloader config always stays the base one (no sweep may change it, `test_sweep_configs`). Only the hyperparam case may lack its tuned config (its sweep still running, or skip_tuning about to write it from the base), any other case raises, so a test that builds such a case's train config writes them first with `tests/tuned_configs.write_hyperparam_tuned_configs`. The base `Study.make_submodule_config(case, submodule_type)` recurses through `make_train_config` on `case.replace_pinned(model_type=submodule_type)`, so submodule configs get their own tuned merge and transfer wiring. The per-model-type specs come from module-level builders the owning study exports and the transport study reuses for its pseudo-types (`scalar_submodule_train_spec` / `structured_power_balance_train_spec` in power_balance_study.py, `profile_train_spec` in profile_study.py), all starting from `NN_INIT_DEFAULTS`. `Case.validate` rejects a case whose ignored axes sit off the values `pin_inapplicable_axes` pins (a frozen mlp), so every spelling of a case is the grid's, and `replace_pinned` is the way to another model type's case.
- **Natural epochs and batches**: one epoch is one pass over the case's own training set, popsim's own definition, so the LR schedule (`transition_frac x len(train_dl) x max_epochs`), the validation cadence and the patience count epochs, and a small training set trains fewer optimizer steps than a large one (accepted by the user 2026-10-13, which ended the fixed steps per epoch of 2026-10-06 to 10-13). Sweeps and production train the same epochs (`max_epochs` = `hyperparam_max_epochs`, 320 in the apsdpp TOMLs), so the tuned schedule is the production schedule. The finetune stage (`Case.trains_on_target_only`: transfer finetunes and exnihilo cases with their p_oh / p_rad prereqs, never the pretrain twins) trains `finetune_max_epochs` with `finetune_patience` instead (locked, 640 / 320 in every apsdpp TOML, `finetune_max_epochs` >= `max_epochs` enforced), its `transition_frac` scaled by max_epochs / finetune_max_epochs (`Study._extend_finetune_budget`) so it decays exactly as a max_epochs run and the extra epochs train on the decayed tail. Why (user, 2026-10-13, `scratch/exnihilo_lr_probe`, extended to profile and transport 2026-10-14): a target-only epoch was 1 to 3 steps at the probe's batch 4096 (still 1 step up to a few shots at every batch), so patience 40 stopped every probed mlp exnihilo run at epochs 52-185, 8 to 108 percent above what 640 epochs with patience 320 select, which match 1280 epochs within 2 percent. Every training loader fills its ragged final batch with samples drawn at random, without replacement, from the full batches of the same epoch (popsim `DataLoader(fill_last=True)`, a new draw every epoch), so every epoch trains on every sample at least once, every batch is full and weighs the same, at one compiled shape, while the validation loaders pad with repeats and trim them. A set smaller than one batch is one partial batch, every step the whole set. `trb_utils.CaseTrainDataLoader` wraps every train loader with the seed's `shuffle_seed` and the `normalizer_fit_ds`. Each loader family's batch sits at or below its critical batch size (user, 2026-10-14, McCandlish et al. 2018, `scratch/critical_batch`): past it a larger batch reaches a given loss in about the same steps and wastes the extra samples, and under natural epochs it trains fewer steps per epoch. `POWER_BALANCE_BATCH_SIZE` 512 (gradient noise scale at the best-validation epoch, plain / Adam: mlp 341 / 534, sciml-taue-nn 284 / 304, transformer 2,017 / 4,121, the mlp's fitted critical batch growing from about 330 to 930 as the loss falls, and every batch from 4096 to the full set taking about the same steps to the same loss), `SCALAR_SUBMODULE_BATCH_SIZE` 2048 (p_oh / p_rad, CPU-only in pb2, p_rad's noise scale 2,070 / 2,619, p_oh's unusable), `PROFILE_BATCH_SIZE` 1024 (mlp 1,235 / 1,577, reservoir 3,064 / 2,195, shape-init 6,000 to 8,400, TORAX unmeasured) and `TRANSPORT_BATCH_SIZE` 1024 (unmeasured, below the PB transformer's noise scale, torax-gyrobohm 268 s and torax-qlknn 347 s per epoch there against 155 and 221 s at 2048), the transport pseudo-types sharing the PB and profile ones. Each constant's comment keeps the largest batch every model of its family fits at its sweep maximum (`scratch/batch_bench_per_model`, A100-80GB, 0.90 XLA pool) for reference. On the hyperparam case that is 93, about 1,100, 194 and 47 batches per epoch, the filled final batch included. Until 2026-10-14 the batches were each family's throughput knee (PB 4096, p_oh / p_rad 393216, profile 8192, transport 2048), about 7x past the PB mlp's critical batch. `Study.batches_per_epoch` measures a loader config's batches per epoch (only the transfer LR reads it, on the historic training set), recorded in the working dir's `batches_per_epoch.toml` by loader-config hash, read back root-most study of the lineage first, and deleted whenever a fresh config lock is written. No sweep may change `dataloader_config` (test_sweep_configs).
- **Weight averaging and the stop rule** (popsim `TrainConfig.ema_horizon_epochs` / `min_relative_improvement`, locked study fields, defaults 5 epochs and 0.01, set by the user 2026-10-14 without a probe): every run trains the live iterate but validates, ranks, checkpoints, restores and tests `Trainer.eval_model`, the average of the trainable leaves over the live model's frozen buffers. Every applied step moves the average by max(1 / horizon_steps, 1 / (t + 2)), horizon_steps = `ema_horizon_epochs` x `len(train_dl)`: the running mean of every iterate, the init included, until the horizon, then an EMA over it (popsim `docs/notebooks/weight_averaging.ipynb`). The finetune stage keeps the same horizon in epochs, so it averages 5 to 15 steps there. Patience counts a validation as an improvement only when the averaged val loss beats the best by more than `min_relative_improvement` of it, which only moves the stop epoch, the checkpoint kept is still the lowest averaged val loss. A checkpoint's `model` item is the average, so every `restore_model` consumer (transfer twins, submodule prereqs, analysis) reads the averaged model, while `Trainer.train_state.model` is the raw iterate (tests compare `eval_model`). Transfer and submodule restores run in `model_init`, before the Trainer exists, so the average starts at the restored weights.
- **Model size axis** (`model_size`, `CaseGridConfig.model_sizes`, default `("sweep",)`, `orchestration/study.model_size_updates`): checks whether a case's architecture size holds it back, without re-sweeping. `sweep` trains the tuned config, `min` / `max` move `SIZE_HYPERPARAMETERS` (nn_width, nn_depth, d_model, reservoir_size) to the ends of the model type's sweep grid, `half` / `quarter` / `eighth` divide the tuned `WIDTH_HYPERPARAMETERS` by 2 / 4 / 8 (`WIDTH_DIVISORS`) and keep the depth (a divided width keeps at least 1, d_model stays a multiple of num_heads and at least num_heads). Everything else stays tuned (learning rate, history_len, n_shapes, num_heads, ...), and the batch size is unchanged since the batches were benchmarked at the sweep maxima. `make_train_config` applies it right after the tuned-config merge, reading the grid through `Study.sweep_config`. Every size shares the plain hyperparam case (pinned in `_hyperparam_field_values` like `target_shot_order`, no config field), and the whole model is sized: the submodule and pseudo-type prereqs (and the `make_submodule_config` they restore through) are built at the case's own size, so sciml-taue-scalinglaw and the transport sciml, which sweep no net of their own (`Study.sweep_model_init_parameters` is empty), are sized through their prereqs. Only the multiobjective anchor-delta prereqs stay the hyperparam cases, and the transfer pretrain twin keeps the case's size. Use it from a child study that sets `[cases] model_sizes = ["sweep", "min", "max", "half", "quarter", "eighth"]` on a restricted slice and borrows the `sweep` cases from its primary.
- `make_cases(cfg)` is generic: the product over the Config's case axes (`CaseAxis` fields, each naming the Case field it feeds), the shared da None / target-shot skip rule, `Case.pin_inapplicable_axes`, then `finalize_cases` (unwrap prereqs, dedupe, sort, drop impossible). cfg is an argument so another config's grid can be rebuilt.
- `run_study` is a base classmethod (Fire CLI reads its signature, so flags live in one place): config TOML parse via `cls.Config`, `clean_working_dir` (clean_models / clean_results / clean_figures, BEFORE the Study is built so a study whose lock refuses the config can still be reset), Study init (config lock), `record_case_grid`, `setup_directories` (clean_sweeps, mkdirs), partition check, `_visualize_data()` (uses the `DATA_VISUALIZATION` ClassVar), orchestration loop + `write_collected_results` (`collect_results` written to `collected_results.nc`, with parallelism in a CPU job of its own through `slurm_utils.launch_collect_results_job`, the orchestrator falling back to collecting itself when the job ends without the file, the result files read on up to `COLLECT_PROCESSES` (16) spawned processes through `study.map_result_files` with a progress line every 20 cases, a cold read being about 3 s of I/O, which processes cut about 14x and threads cannot: netCDF4 segfaults under threads and h5netcdf serializes them), then `run_analysis(enable_parallelism)`. Each study module's `fire.Fire` main maps `run_study` and `reset_study` straight to its class's classmethods. `reset_study` starts a study over: it refuses while any job of the study is queued on any partition, deletes the whole working dir and the wandb sweeps of the study's own hyperparam cases, then writes a fresh config lock. A lineage resets root-first, so every child's lock records its parent's fresh stamp before any orchestrator starts (`bash studies/hs1/launch_hs1.sh [chain ...]` resets the named hs1 chains and submits them, each child after its primary has started). The run_study clean flags refuse to run with parallelism, so the reset is the way to start a parallel study over.
- **Sweep trials preempt and resume** (popsim `launch.finish_sweep_run`): a trial cut by the wall budget marks itself preempting and finishes with exit code 1, so wandb holds it out of the bayes fit and requeues it, and the next agent resumes it under the same run id from `Study.sweep_checkpoint_dir(case)/<run id>` (`launch_sweep` sets `resume` and the root, popsim's `_run_train` nests the run id and inits with `resume="allow"`). So every trial trains to its max epochs or patience whatever device and job length it ran on, and a preempted trial stays outstanding in `get_completed_runs`. `_finalize_sweep` and clean_sweeps delete those checkpoints. The patience count (popsim `EarlyStopping.state()`) is saved in every checkpoint's metadata and restored on resume, strictly: a checkpoint without it raises. A resumed run continues the live iterate from the checkpoint's `raw_trainable` item and the average from its `model` item, and each epoch's shuffle is keyed by the epoch number (popsim `DataLoader.set_epoch`), so it trains on the batches an uninterrupted run would.
- **Seed results** (`orchestration/seed_results.py`): every production case trains `num_seeds` independently seeded runs, each its own SLURM job (`train_{case}.seed_{s}.{study}`), which sets the model init (`prng_seed`) and the training shuffle (`shuffle_seed`, keyed in `CaseTrainDataLoader`), trains into `trained_model_dir(case)/seed_{s}` keeping only its best (averaged) checkpoint beside the latest one it resumes from, and writes the test results of its best checkpoint to `results/<case>/seed_{s}.nc` (`seed_result`, attrs that checkpoint's epoch and val loss). Once every seed has its result the orchestration pass merges them (`Study.merge_seed_results`): the case result keeps every error variable of each seed on a `seed` dim (float32, each seed's best epoch and val loss beside them, attr `result_best_seed` the seed with the lowest val loss), the pred / targ variables are the best seed's, the best seed's best checkpoint moves up into `trained_model_dir(case)`, which every unseeded restore reads (sweep trials, `restore_trainer`), and the seed dirs and seed results are deleted. A case with `Case.keeps_seed_checkpoints` (a transfer_pretrain twin, or a model type in the study's `Case.RESTORED_MODEL_TYPES`) copies that checkpoint up instead and keeps each seed's best checkpoint in its seed dir, dropping only the resume checkpoints. Each step of a merge is skipped once done and the result file is written last, so a merge cut short reruns cleanly, and a case counts as finished (its dependents start) only once merged. Every case score is computed per seed and reduced by `seed_statistics` to three values: `<name>` the seed mean, `<name>_best` the best seed's and `<name>_seed_std` the sample std over the seeds (ddof 1), the run-to-run spread a difference between cases has to beat. Seed s of a case restores seed s of every case it restores from (`Study._seeded_train_config` repoints `transfer_checkpoint` and each direct `submodules` checkpoint_dir), so the seed spread of a transfer finetune or a sciml composite holds the spread of its twin and submodules too, while `make_train_config` itself still points at the merged best. Comparison figures plot the seed mean with the seed std as the error bar, tables carry all three for the headline metric, and case reports rank and title by the best seed, whose predictions they plot. Until 2026-10-13 one run per case kept its top `num_result_checkpoints` checkpoints on a `ckpt` dim instead (about 377 files per case).
- **Checkpoint format** (`trb_utils.CHECKPOINT_FORMAT` = `"minimal"`, popsim `TrainConfig.checkpoint_format`): every checkpoint of the study is one uncompressed `<epoch>.npz` file that popsim writes, prunes and restores itself (`popsim.ml.checkpointing.MinimalCheckpointManager`), the leaves keyed by `<item>/<jax keystr>` beside the metadata and metrics JSON, so numpy alone opens it (`model/...` the averaged model, `raw_trainable/...` the live iterate for resume, `opt_state/...`). A finished case holds one file. orbax's format (popsim's default, kept for large or sharded models) took about 40 files per checkpoint and ran the scratch inode quota out on 2026-10-13. Every path that names a checkpoint goes through `checkpoint_step_path` / `saved_checkpoint_steps` with the constant, and `convert_checkpoints` rewrites a checkpoint dir in the other format given a TrainState template (`build_train_run`), carrying every item, the metadata and the loss.
- `collect_results` schemas intentionally differ: the base implementation emits the per-case scalar summary (dims: case_idx) via `_summarize_case_errors` (each statistic per seed, then `seed_statistics`), which power balance and transport both inherit unchanged, and profile overrides it with a per-shot long-form dataset (dims: record, seed means). All use the base `case_coords` driven by `case_coord_names()` (case_idx plus the case-axis Case fields).
- `run_analysis`: power balance and transport call `orchestration/case_analysis.run_summary_analysis(study, enable_parallelism, LAYOUT, COMPARISON_FAMILIES, TABLE_SPEC)` (transport with `figures_from_metrics=True`, so its figures are the stage grid of `collected_metrics.nc` like the profile study's, power balance's the 2x2 grid of `collected_results.nc`), profile runs the same steps itself plus its freeze-shapes and TORAX relaxation figures. With parallelism the per-case analysis (stage metrics + case report) fans out as one SLURM CPU job per case (`run_case_analysis_parallel`), and the serial paths afterwards skip finished cases. Each study names its own pieces in two ClassVars that `orchestration/case_metrics.py` and `orchestration/case_reports.py` resolve with import_module: `ANALYSIS_METRICS_MODULE` exports `METRIC_NAMES` and `case_timeslice_metrics(study, case, result_ds)` (a `StagedTimesliceMetrics` record per valid test timeslice, one column per seed, `best(name)` the best seed's), `ANALYSIS_REPORTS_MODULE` exports `case_report_done(case_dir)` and `render_case_report(result_ds, ts_metrics, case_dir)`. The shared side holds `staged_result_records` (the per-shot read of a result file every metrics module uses: the nearest-time join, the stage labels from `stages.segment_stages`, the records of every clock-advancing timeslice with a target), the per-stage aggregation (each stat per seed, then `seed_statistics`), the per-case `case_metrics.nc` caches combined into `collected_metrics.nc` (`collect_metrics`), and `best_worst_pdf`. Every test suite writes `error_diverged_ts` (1 where the prediction went non-finite, 0 where finite, NaN without a target, outside the freshness mask like the validation divergence penalty) and NaN instead of any non-finite error, so a blow-up stays a record whose errors the means skip, and every study reports the diverged fraction (`diverged_mean`, a table column, also a transport figure row). The profile and transport studies score the validation chi itself: the shared `ProfilePredictorTRB.make_test_eval_suite` writes `error_chi_value_ts`, `error_chi_grad_ts` and `error_chi_ts` (value + `gradient_weight` x gradient, the per-timeslice validation loss less the device weight, fresh-masked in the transport study) from the `loss_config` its `test_eval_suite_config` shares with the val suite. The transport study's own metrics module adds that chi (headline `combined`) to the power balance abs / rel / diverged metrics, NaN chi for the scalar prereq cases, and its reports rank its profile results by time-averaged chi, each page only the chi traces over the shot (the predicted profile maps took most of the rendering time, about 13 minutes per case), and render scalar prereq result files with the power balance page. Comparison figures come from `orchestration/comparison_figures.comparison_figures(ds, layout, family, figure_dir)`: each study's plotting.py declares a `ComparisonLayout` (panel rows and columns, the per-panel stats, the case-grid fields with their filename tokens) and its `COMPARISON_FAMILIES` (a line per value of one field, a figure per combination of the rest, `min_series=2` for the families only a child study varies: target_shot_order, freeze_submodules, multiobjective). exnihilo only exists without adaptation, so `ComparisonFamily.include_exnihilo` (set on every training_dataset_comparison) also draws the exnihilo cases in the figures that fix another domain_adaptation, beside the historic sets' adapted ladders. The shared `TD_LABELS` / `TD_COLORS`, `FREEZE_*` and `MULTIOBJECTIVE_*` maps live in comparison_figures.py. Each study's tables.py declares a `ComparisonTableSpec`, and the writer plus the shared power balance / transport per-case frame live in `orchestration/tables.py`. Power balance per-shot errors in result files are raw time integrals (long shots score worse), so its study_metrics and case_reports rank shots by TIME-AVERAGED error instead (`shot_time_averaged`).
- Other subclass ClassVars: `SWEEP_CONFIG_DIR`, `STUDY_TYPE`, `DATA_VISUALIZATION`, `CHI_VALIDATION_LOSS` (profile and transport, injects `chi_sigma_floors` and `train_chi_sigma_floors`), `RESIDUAL_SCALE_LOSS` (power balance and transport, injects `residual_scales`), `ANCHOR_DELTA_MODEL_TYPES`, `TUNED_LOSS_KEYS`.

**Hyperscrabble (parent studies)** (`orchestration/lineage.py`): a study may name a `parent_study` of the same type under the same working_dir_base, and borrows read-only every case an ancestor has trained or whose current grid (as the ancestor's config lock records it) will train. So a secondary study along a restricted axis trains only its new cases, e.g. a frozen-vs-unfrozen comparison on one normalization and one da trains only the frozen cases and borrows the rest, hyperparam and submodule prereq cases included. Chains recurse (tertiary -> secondary -> primary).
- A child refuses to start unless every LOCKED field equals each ancestor's (a borrowed case is only the same model under the same setup).
- Ownership is root-first: `Study.case_home(case)` is the root-most ancestor that claims the case, else the study itself, so every study of the chain agrees where a case lives and a borrowed case is never rebuilt around another study's prereqs. A nearer study holding its own copy of a case an ancestor now claims (the ancestor's grid grew) raises instead of mixing.
- `trained_model_dir`, `result_path` and `tuned_config_path` route through `case_home`, which covers every cross-case read (tuned configs, transfer checkpoints, the submodule checkpoint_dir nested in a TrainConfig, analysis). launch_train / launch_sweep / the tuned-config writes call `_require_local`, `run_unfinished_cases` only waits on borrowed cases ("waiting on <ancestor>"), the watchdogs and clean_sweeps see local cases only, and `trb_utils.restore_from_checkpoint` raises on a missing dir instead of letting the checkpoint manager create one in an ancestor.
- Freshness is transitive: each lock records its parent's stamp at creation, `refresh_lineage` reloads the chain every orchestration pass, and a reset ancestor (clean_models / clean_results) stops every descendant until it is cleaned too.
- Analysis stays local: `case_metrics.nc` lives in the study's own result dir (a borrowed case reads its home's cache when present), borrowed cases get no case report (their home renders it), figures, tables and collected results cover the whole grid.

CRITICAL: `str(case)` names checkpoint dirs, result files, tuned-config paths, wandb projects, and SLURM job names - byte-level drift orphans existing runs. `restore_predictor.checkpoint_to_profile_case` parses case-directory names back into Cases and must stay in sync with `__str__`. `Study.case_by_name` finds a case of the study by that string (the analysis jobs and `plot_torax_evolution` use it). Each study's `tests/<study>/test_*_case_naming.py` pins the literal case strings.

**Input normalization as POPSIM modules** (`modules/normalization.py`): the power-balance models take the same 7 physical inputs (`ip_MA, b_geo, geometric_axis_r, minor_radius, elongation, n_e_line_average_1e20, power_additional_MW`) plus `ds_source_idx`. Each model owns an `InputNormalizer` (`raw` identity, `physics` dimensionless, `zscore` per-device, `coral` per-device covariance alignment, and the `physics-coral` / `physics-zscore` stat stages fitted in the physics feature space, whose classes subclass the plain ones and only swap the `features` hook), fitted from TRAINING data only at model_init and stored as frozen buffers (they checkpoint with the model but are never trainable - trainable selectors pick `module.nn` leaves explicitly). CORAL (`fit_coral_stats`) aligns every device's covariance to the TARGET device's: the target keeps the identity transform and needs only 1 complete shot, a source device needs `MIN_CORAL_SHOTS` shots or keeps the identity, and features without target spread or with degenerate device spread keep identity slots. CORAL is therefore a no-op when the fit data holds no target shots (every da None case on the source devices, the hyperparam cases among them) or only target shots (exnihilo), and acts in weighted / addition / transfer cases from 1 target shot. The per-device z-scores instead leave a device absent from the fit data unstandardized beside standardized sources. So `Study.Case.is_impossible` drops every `STAT_NORMALIZATIONS` case scored on the target with 0 target shots, the z-scores as ill-posed and CORAL as a duplicate of its stateless method, and every exnihilo `CORAL_NORMALIZATIONS` case, a duplicate too, and with them any case built on such a prereq. The da None cases train and score on the sources alone, so their z-scores are well-posed and they stay. The profile and transport studies' counterparts are `profile_predictor/module.make_nn_input_normalizer` (10 dimensionless `nn_inputs`) and `transport_predictor/module.make_transport_nn_input_normalizer` (those 10 slots from the measured Wtot plus `paux_norm`), thin wrappers over the shared `normalization.make_feature_normalizer` + `feature_fit_arrays` (feature matrices built with `flat_columns`), which hold the one method dispatch (`physics` identity / `physics-coral` / `physics-zscore`, `FEATURE_NORMALIZATIONS`). They share the contract of `make_normalizer`: fit data `None` yields identity buffers with the checkpoint's pytree structure. All three studies' TRBs pick the fit dataset through `trb_utils.normalizer_fit_dataset` (skipped entirely when a transfer checkpoint will overwrite the buffers), pass `trb_utils.target_device_idx()`, and index `data_normalization` strictly. `organize_data.normalize_domain` implements the same math on one combined dataset for data visualization only, with `feature_space` selecting which family's features the physics* methods run on (`power_balance` = the 7 `physics_feature_vec` slots, `profile` = the 10 `nn_inputs`, `transport` = the 11 transport features).

**Module pattern**: Predictors inherit from POPSIM's `TimeIndepModule`/`TimeDepModule`. Profile predictor (time-indep) predicts Te/ne on a uniform 51-point `rho` grid over `[0, 1]` (not psi_n). Model families: `shape-init-pca` / `shape-init-kmeans` (point shapes from an uncentered PCA or k-means of the unit-integral training profiles, weighted by an NN, shapes optionally frozen), `mlp`, `reservoir`, and `torax-constant` / `torax-gyrobohm` / `torax-qlknn` (differentiable TORAX simulation with NN-predicted transport/edge/source parameters, `torax-cgm` was cut on 2026-10-01). The shared `TORAX_CONFIG_BASE` (profile `train_configs.py`) sets Z_eff 1.5 over TORAX's default neon impurity and holds no impurity line radiation, no cyclotron radiation and no `generic_current` (TORAX's default drives 20 percent of Ip at rho 0.4), and `torax_module.clamp_core_profiles` clips the evolving profiles after every solver step, an exact identity in range so nothing drifts per step (a softplus clamp there removed 2-27 eV per call until October 2026). The profile relaxation keeps the base solver, one linear step with Pereverzev at the TORAX defaults, whose progress per step does not depend on dt, so its output is N damped steps from the parabolic initial profiles rather than a steady state. The step is fixed at `trb.RELAXATION_DT_S` = 25 ms and `n_solver_steps` (default 8, swept over 4 / 6 / 8) is the only window knob, `trb.relaxation_numerics` turns it into the TORAX numerics. Every TORAX network predicts dimensionless values that the shared bound functions turn into TORAX units: the density pinch as the peaking rate c = V a / D (`density_peaking_rate`, d ln n / d rho_norm in a source-free steady state, so one range means the same peaking on every device, `bound_transport_coefficients` takes the minor radius), the constant model's chi_i / chi_e / D_e as multiples of chi_ref = a^2 / (5.8 `TAU_REF_S`), the BGB and QLKNN knobs as multipliers, the fueling and heating as multiples of nebar x volume_approx / `TAU_REF_S` and w_approx / `TAU_REF_S` (`TAU_REF_S` = 50 ms in torax_module), and the edge BCs as fractions of nebar and te_approx. Every family builds its Outputs with `profile_outputs`, and the shape-init, MLP and reservoir families share the decode `assemble_profile_outputs` over `scaled_profile_points` (ne points, te points, then a te and an ne scale correction that multiply them). The MLP and reservoir are the purely data-driven families: they see only the normalized features, no n_e_line_average or te_approx scale enters their outputs. shape-init is a SciML family (user, 2026-10-14): its shape combinations are unit-integral, so it scales the ne points by the measured n_e_line_average and the te points by te_approx before the decode (`ProfilePredictorShapeInit.__call__`), which in the transport sciml makes te_approx of the state-implied beta the direct link from the predicted Wtot to the Te magnitude. The k-means basis is fitted with the case seed's `prng_seed`, so each training seed clusters on its own (the PCA one is deterministic). torax-* model types additionally carry a `geometry_builder` case axis (`circular` or `miller`, see `torax_module.build_circular_geometry_jax` / `build_miller_geometry_jax`). The circular builder is TORAX's own model: it labels surfaces by the midplane radius and its q carries TORAX's 1.25 correction. The miller builder labels them by the normalized toroidal flux radius the data is stored on, inverting it from the vacuum toroidal flux of each Miller contour, and its CHEASE geometry type leaves q uncorrected. Its shape profiles come through the coefficient dict (`geometry_shape_coefficients`, closures in `miller_shape_coefficients` for now): the magnetic axis keeps 0.7 of the LCFS elongation excess, and the axis Shafranov shift is (a / 2R)(beta_p + l_i / 2) of the minor radius with l_i 0.8, capped at 0.3 a. No default is suppressed from `str(case)` for this axis (every case gets an explicit `geom_` token), and it is deliberately NOT a `HYPERPARAM_FIELDS` entry so `miller` cases get their own hyperparameter sweep and tuned config instead of inheriting circular's. Power balance (time-dep, simple-Euler stepper, `energy_mhd_MJ` state) predicts stored-energy evolution with five architectures: `sciml-taue-scalinglaw` (H89/H98 tau_e blend gated by a P_LH scaling, consumes PHYSICAL units, prefactors trained as their logs and every coefficient exempt from weight decay via `SCALING_LAW_FIELDS`, called `scaling_law` before July 2026), `sciml-taue-nn` (bounded NN tau_e, called `sciml` before July 2026), both on the shared `PowerBalanceTaue` step dW/dt = P_aux + P_oh - P_rad - Wtot/tau_e with only `predict_taue` differing, `mlp` (`PowerBalanceMLP`, an MLP predicts dW/dt from the normalized inputs and its own predicted Wtot, the feedback that keeps the rollout from being an open-loop integrator. Its normalizer, like the transformer's (`MODEL_TYPES_WITH_ENERGY_INPUT`), is built `with_energy`: Wtot is an 8th slot (MJ for raw / coral, beta_N with b_geo for the physics methods, per-device z-scored for the zscore methods, inside the CORAL alignment for coral) and `energy_rate_scale` maps the NN output back to dW/dt (MW for raw / coral, the normalized energy unit per `TAU_REF_S` = 30 ms otherwise), so both sides sit near 1. Called `unstructured_nn` before July 2026), and `transformer` (recurrent causal attention: a rolling buffer of the past PREDICTED Wtot values is carried in the module State as a discrete `discrete_no_save_field`, seeded with the measured t0 Wtot tiled, and the embedded-input query attends over embedded Wtot tokens plus a learned per-slot position embedding, needed because scalar tokens are otherwise permutation-invariant - see `popsim/modules/delay.py` for the discrete-state pattern. Every buffered Wtot goes through the normalizer's energy slot at the current inputs and the head output through `energy_rate_scale`, as in the mlp), and its `multiobjective` case axis (`MULTIOBJECTIVE_MODEL_TYPES = ("transformer",)`, a `HYPERPARAM_FIELDS` entry so a multiobjective case tunes on the plain transformer's sweep, called the `transformer-multiobjective` model type until October 2026): `PowerBalanceTransformer` with `predicts_powers` has two more head outputs predicting P_oh and P_rad on the `energy_rate_scale` power scale, never fed into the Wtot update, and its target_vars carry the measured powers so the sciml anchor terms train them, multi-objective learning compared against the plain transformer in hs1_pb_multiobjective). `sciml-taue-scalinglaw` and `sciml-taue-nn` hold `p_oh` / `p_rad` submodule predictors trained as their own prereq cases and restored from checkpoints. Each predicts its power as a scale (|Ip| for P_oh, the line density for P_rad) times `scalar_power.leaky_softplus` of its network, softplus plus a `POWER_LEAK_SLOPE` = 0.01 linear leak, so a network pushed far negative keeps its gradient and the power may dip slightly below 0 (the scaling law clips P_aux + P_oh at 0.001, `bound_wtot_dot` bounds dW/dt). The Wtot loss counts only the `fresh_equilibrium` timeslices (the stores hold the reconstruction's signals forward between reconstructions), its training residual divided by the device's typical stored energy (`residual_scales`, so every device weighs alike and `huber_delta` is a fraction of it), its validation the absolute error in MJ, a `trb_utils.TimeAveragedLoss` over each episode's fresh time, and the p_oh cases train and validate on those timeslices only (`fresh_var` in `SCALAR_SUBMODULE_SETTINGS`, the test still scores every timeslice). During joint training the loss anchors the submodule predictions to the measured `power_ohm_MW` (fresh timeslices only) / `power_radiated_MW` (every timeslice) targets (`anchor_weight_power_ohm` / `anchor_weight_power_radiated` loss keys, 0.1 each, an untuned prior, each a huber of the residual over the device's typical power at the tuned `huber_delta` of the hyperparam p_oh / p_rad case, training loss only so `val/loss.mean` stays pure Wtot, no-op for cases whose target_vars lack the powers, a multiobjective transformer's power heads get the same anchors and so depend on the hyperparam p_oh / p_rad cases). The p_oh / p_rad submodule training losses divide their residuals by the device's typical power too, their validation stays absolute in MW and the optimizer runs the submodules at a reduced learning rate (`submodule_lr_factors` in the power balance `base_optimizer_config`, default 0.1x, applied by pytree-path labeling in `trb_utils.make_grouped_exponential_adamw` via optax multi_transform). Transport predictor (time-dep, simple-Euler stepper, `modules/transport_predictor/`) predicts ne/te profile EVOLUTION on the same rho grid from the power-balance inputs plus triangularities (no measured betan - beta quantities derive from the evolving state Wtot): `transformer` (rolling profile-history buffer as discrete state, same shape as the power balance transformer: current-feature query attends over position-embedded profile tokens, each a peak-normalized history row plus its ne and te peaks - only predicted profiles are kept as history, never past input features, and the next profiles come out of the same `scaled_profile_points` decode with no n_e_line_average or te_approx scale. A multiobjective transformer has two more head outputs after the decode's rows (the decode reads its corrections at negative indices, so the head output is sliced first): the stored energy as W_p (1 + nn) over the profile-implied W_p and the ohmic power as W_p / `TAU_REF_S` nn, never fed back into the profiles), `sciml` (composes a trained PowerBalance for the Wtot state and a trained ProfilePredictor fed the state-implied betan, its Output surfaces `energy_mhd_MJ_pred` / `power_ohm_MW_pred` / `power_radiated_MW_pred` so the training loss can anchor them to the measured signals - `anchor_weight_energy_mhd` / `anchor_weight_power_ohm` / `anchor_weight_power_radiated` loss keys, training loss only, no-op for the cases whose target_vars lack the signals (all but sciml and the multiobjective ones) - and the optimizer runs the whole power_balance subtree at a reduced learning rate via `submodule_lr_factors` while the profile predictor keeps the full schedule, same `make_grouped_exponential_adamw` mechanism as the power balance study), and `torax-*` (one TORAX solver step of the 1 ms dataset timebase per call, config from `transport_predictor/train_configs.make_transport_torax_config`, whose solver comes from `TRANSPORT_SOLVER_BLOCKS`: one corrector iteration, without Pereverzev for constant / gyrobohm and with it for qlknn (each iteration costs about one more full step), since a corrector-free step solves n dT/dt instead of d(nT)/dt at any dt and the default Pereverzev damps shape changes by ~dt chi / a^2. the rebuild config does not evolve psi within the step since it re-derives psi from Ip every step, the carry config does. The transport config also turns on Angioni-Sauter neoclassical transport, neoclassical chi, D and V with the Ware pinch at about 1.1x per step, which the profile relaxation leaves off). Every torax-* Output also carries TORAX's own stored energy (`W_thermal_total`, ions at T_i, no fast ions) and ohmic power (`P_ohmic_e`, j_ohm E over the Sauter resistivity at the state's T_e and Z_eff) from the post-processed outputs of the seeded state at the reported time (`TransportPredictorToraxBase.inferred_outputs`), which only a multiobjective case anchors. There is no P_rad output: TORAX's core radiation is 2-10 percent of the measured DIII-D P_rad at any plausible Z_eff (divertor and edge radiation dominate), so Mavrin impurity radiation stays off. Unlike the profile study's TORAX modules, which infer the heating magnitude with an NN, the transport ones feed the MEASURED `power_additional_MW` straight to `sources.generic_heat.P_total` and let the sources network predict only the deposition shape, the gas-puff fueling, and `absorption_fraction = 1 - exp(-softplus(nn) * n_e_line_average_1e20 * a)` - a Beer-Lambert shine-through form over the line-integrated density that is always in (0, 1) and never gradient-dead at saturation. The profile modules keep the fixed config absorption of 0.9, where it would be degenerate with their NN-predicted `P_total`. torax-* carry both the `geometry_builder` axis and a `torax_state` axis ("rebuild", `TransportPredictorTorax`, re-seeds TORAX from stored ne/te each step with T_i := T_e and psi from Ip, "carry", `TransportPredictorToraxCarry`, also keeps T_i and psi as plain cell-grid arrays and re-enters them each step through `initial_psi_mode` "profile_conditions" with the current evolving, which reproduces TORAX's own continued evolution to machine precision. A carried TORAX `SimState` pytree crashes every popsim state partition, `CellVariable` rejects the None-filled halves, so no TORAX pytree may enter a module State). In this study (unlike profile_transfer) both axes' defaults ("circular", "rebuild") are suppressed from `str(case)`, and neither is a `HYPERPARAM_FIELDS` entry. The transport `multiobjective` case axis (`MULTIOBJECTIVE_MODEL_TYPES` = transformer and torax-*, a `HYPERPARAM_FIELDS` entry so a multiobjective case tunes on the plain case's sweep, sciml pinned since it always anchors) puts `MULTIOBJECTIVE_TARGET_VARS` (energy_mhd_MJ, power_ohm_MW) into target_vars so the existing anchor terms train them, while every top-level case loads the measured powers (as extra_vars when not anchored) so all train on the same segments. Normalization is not a case axis in the transport study (unlike profile, where it is): a study-wide `data_normalization` config field ("physics", "physics-coral", or "physics-zscore") controls the per-device stat stage (`CoralFeatureNormalizer` / `ZScoreFeatureNormalizer`) over the 11 transport features. `TransportPredictorEnv` (in module.py) seeds each architecture's state from the measured t0 signals carried in the dataloader's state_vars.

**Profile loss split** (`profile_predictor/trb.py`, mirrored in `transport_predictor/trb.py`): the training and validation losses must stay different. Training (`get_loss_fn`, `trb_utils.huber_profile_loss`) is the huber of chi: the residual of the values and of the GP-fit gradients in units of their error bars, floored per device at `train_chi_sigma_floors` from the case's own training shots (the gradient term masked to rho below `GRAD_RHO_MAX` = 0.9, one cut shared by the training losses, the validation chi and the analysis chi, beyond which the GP fits extrapolate into the pedestal), with the swept `huber_delta` / `huber_delta_grad` in error bars (defaults 1 and 3), times `CHI_TRAINING_LOSS_SCALE` = 0.01 so an untrained network scores about 1. Inside a delta it is chi^2 / 2, so a point with a large error bar pulls gently but never with zero force (the user's rule: never a deadband). The math of every study's losses is written out in `presentations/preprint/loss_description.md`. Validation (`get_val_loss_fn`, the sweep metric `val/loss.mean` and the checkpoint selection) is chi, the residual in units of the GP-fit error bar (`trb_utils.chi_value` / `chi_gradient`, the gradient term masked to rho below the same `GRAD_RHO_MAX` and weighted by `gradient_weight`). Each error bar is floored per device and channel at `chi_sigma_floors`, the `CHI_SIGMA_FLOOR_PERCENTILE` percentile of that device's positive peak-normalized fresh error bars over every shot (`trb_utils.chi_sigma_floors`), which `make_train_config` injects into the loss config of every `CHI_VALIDATION_LOSS` study, so the reported chi is one metric across every case. Chi reads no huber delta, so no swept delta can game the sweep metric. A non-finite prediction scores the chi of its finite points plus `divergence_penalty_val` (1e4, `trb_utils.replace_diverged_profiles`, so one diverged TORAX relaxation cannot turn `val/loss.mean` NaN, which early stopping never counts as best), while its training loss stays non-finite so popsim masks the sample out of its step. The test suite writes the same chi per test timeslice and seed, which `profile_transfer/study_metrics.py` reads back. The transport losses use the same per-channel terms (`trb_utils.huber_profile_loss` / `chi_profile_loss`, so its target_vars carry the GP-fit gradients and their error bars, NaN exactly where the values are on every device) and add a freshness mask: the value and gradient terms are multiplied by the `fresh_profile` target var so forward-filled timeslices steer neither training nor checkpoint selection, the anchor terms ignore that mask and are training only, each a huber of the residual over the device's typical value with the tuned delta of the hyperparam power_balance / p_oh / p_rad case (a multiobjective case depends on the hyperparam power_balance and p_oh cases), weights 0.1 each, the stored-energy and ohmic power anchors counted at the `fresh_equilibrium` timeslices and P_rad at every one (`trb_utils.freshness_weight`), training averages the two channels where chi sums them, a non-finite rollout leaves its training loss non-finite so popsim's train step masks that sample and steps on the rest (a finite stand-in would leave the gradient NaN through the rollout's own backward pass, popsim would skip the whole step, and a one-batch target-only epoch would abort, `tests/modules/transport_predictor/test_training_divergence.py`), and validation replaces it by the target and charges the chi-scale `divergence_penalty_val` at the fresh slices. The validation loss is a `trb_utils.TimeAveragedLoss`, each episode's loss integral over its fresh profile time, so a long DIII-D shot weighs no more than a short MAST one. The transport top-level sweeps tune `huber_delta_grad` like the profile study's.

**Domain adaptation / transfer modes** (`domain_adaptation`): `none` (train and test on the same device(s), baseline and hyperparam case), `weighted` (add a small amount of highly-weighted target data during training, weights from `Study.make_weighted_device_weights`, called `mixing` before July 2026, so old run artifacts may carry the name), `addition` (add target shots to the training set as normal samples, no weighting - identical datasets to `weighted`, differs only in the absence of `device_weights`), `transfer` (pretrain through the `transfer_pretrain` twin, restore its checkpoint, fine-tune the last layers on the target). The twin (`Study.Case.transfer_pretrain_case`) trains on historic data with checkpoint selection on the target test set. A stat normalization fits its statistics on historic + the case's n target shots, so its twin keeps n, while the stateless ones (raw, physics) share one twin at `HYPERPARAM_TARGET_SHOTS`. A transfer finetune (its p_oh / p_rad prereqs too) trains at the tuned lr0 / sqrt(the batches per epoch of the historic training set) on the tuned schedule (`Study._scale_transfer_lr`), whatever the finetune's own size: the set its twin trains on (every source device's train and val shots), measured once per loader family on the 0-shot split since that set does not depend on the target split (about lr0 / 10.6 for power balance, / 15.5 for profile, / 7.5 for transport, / 35 to 37 for p_oh / p_rad at their batch of 2048). An exnihilo case trains at the tuned lr0. Both train the finetune stage's epochs and patience (see Natural epochs and batches). Earlier rules (all superseded 2026-10-13): lr0 / steps_per_epoch clipped to [0.01, 1] on a flat schedule for transfer, then lr0 / (2 x steps_per_epoch) for transfer and exnihilo under the fixed steps per epoch. The `exnihilo` training-data option trains from scratch on the target device only. The target split lives in `orchestration/target_shots.py` and is decided on the POWER BALANCE view of the target device in every study, so a transport case and its power balance and profile prereqs train and test on the same shots (`organize_data._split_target_shots` then indexes the study's own view by shot number and raises if its prep dropped one). The test set is never trained on (num_target_shots = -1, the old all-shots cheating reference, was removed in October 2026): exactly one of `target_test_set_size` (the highest-hazard shots) or `target_test_shots` (every shot at or above the hazard rank of the lowest named shot) defines it. Hazard = per-shot p95 of normalized (energy_mhd_MJ^2 + ip_MA^2)^0.5, called "performance" before July 2026, computed in `get_ds` on the full 0D series BEFORE the per-study prep. Every other target shot is the training pool, and the `target_shot_order` case axis picks num_target_shots of it: `ascending` (the base extrapolation, lowest hazard first, no name token), `descending` (the highest-hazard pool shots, closest to the test regime) or `spanning` (each shot's footprint is 32 evenly spaced complete timeslices of the 7 power balance inputs plus energy_mhd_MJ, z-scored over the pool, shots differ by their exact Gaussian-kernel MMD with the median-heuristic width, 1 shot is the MMD medoid, 2+ start from the most different pair then go farthest-first, so picks are nested from 2 up, ~7 s for the ~710-shot MAST pool). An order only applies with target shots in training, so every order shares the hyperparam case and the stateless transfer twin, while the stat-normalization twin and the submodule / pseudo-model-type prereqs keep the case's order. Domain-adaptation cases reuse the test set for checkpoint selection (no separate val set, slightly optimistic but consistent).

### Config

- Field roles (`transport_study/config.py` module docstring): every Config field declares one with its type. `Identity[T]` (study_name, parent_study) names the study, its working dir and the study it borrows from. Unmarked fields are LOCKED (anything that changes what a case produces under an unchanged name: datasets, target, debug, max_ds_size, epochs, patience, the EMA horizon and its stop tolerance, sweep size, test set size and named test shots, dataset_fractions, num_seeds, every hyperparam_* field, transport's study-wide normalization and submodule variants), the default on purpose so a new field can never silently mix results. `Annotated[T, CaseAxis(<Case field>)]` marks a case-grid axis, free to change between runs. `Orchestration[T]` marks where and how jobs run (partitions, limits, wandb, working_dir_base), never locked. `fields_with_role`, `case_axes` and `differing_fields` read the markers.
- Study TOMLs mirror the roles: identity and locked fields at the top level, axes under `[cases]`, orchestration under `[orchestration]`, device paths and `target` under `[datasets]` (`PTPS_DATASET_PATHS` supplies default devices). A field outside its role's table raises naming the right one.
- Config lock (`orchestration/config_lock.py`, `config_lock.toml` in the working dir): identity + locked + case-axis fields and a final `[lock]` table (study_type, stamp, the parent's stamp), no orchestration fields, written atomically. Every Study init refuses a config whose identity or locked fields differ (naming them). Only `run_study` rewrites the recorded axes (`record_case_grid`), analysis jobs and plotting never do. A lock is only created over empty models/ and results/, so deleting one by hand cannot vouch for stale results, and clean_models / clean_results delete it. The lock reader takes the `[datasets]` paths alone (no env merge) and drops fields the class no longer has with a warning.
- `transport_study/config.py`: `StudyConfig` (Pydantic, frozen, global one-shot proxy `config`, `config.get_instance()` for the object itself), reads `PTPS_*` env vars. `debug` keeps every target shot but caps each source device at its `DEBUG_MAX_SOURCE_SHOTS` most recent shots (in `get_ds`), the epochs at `DEBUG_MAX_EPOCHS` (12), the validation interval at `DEBUG_EPOCHS_PER_VAL` (3), the sweeps at `DEBUG_HYPERPARAM_SWEEPS` (1 trial) and the seeds of every case at `DEBUG_NUM_SEEDS` (2, a CaseGridConfig validator). So a debug run validates 4 times, patience never fires, and the TOMLs keep their production values. `wandb_entity` (`PTPS_WANDB_ENTITY`) is required for sweeps, every sweep, agent and API read uses it
- CPU training (`Orchestration` fields under `[orchestration]`, every apsdpp TOML sets them): `gpu_only_model_types` train and sweep on GPU partitions only, `cpu_only_model_types` on the CPU partitions only (p_oh and p_rad in apsdpp, which train as fast on CPU), and every other model type is CPU-capable and may also train and sweep on `cpu_partition`, then the `cpu_fallback_partitions` (`PTPS_CPU_*`) (`Study.training_devices`, a `slurm_utils.TrainingDevices`, both lists without env var, checked against the study's `FIELD_CHOICES`, prereq pseudo types by their own name, never overlapping). Without a `cpu_partition` every type trains on GPU, so once there is one every slow type must be listed GPU-only (until 2026-10-13 the one list `cpu_model_types` named the CPU-capable types, an unlisted type was GPU-only), with `cpu_train_cpus` per CPU job, `train_mem` the `--mem` of every training and agent job on both devices (a CPU job also holds the device arrays, hs2 uses 16G for power balance, 48G for profile and 80G for transport, whose production training processes peak at ~62 GB), and `cpu_capable_buffer_gpus` the idle primary GPUs a CPU-capable case leaves for the GPU-only cases of any study (it replaces `buffer_gpus` for them). `buffer_gpus` (at least 0) leaves idle primary GPUs for others, `gpu_pending_jobs` and `cpu_pending_jobs` let that many GPU-only jobs wait on the primary GPU partition and jobs wait on each CPU partition beyond what fits now, so SLURM refills a freed slot without waiting for the next pass. A CPU-capable job never waits for a primary GPU. Each pass (`Study._launch_ready_cases`) places the GPU-only cases first, then the CPU-only ones, which never take a GPU, then the CPU-capable ones on the leftover primary GPUs, else the CPU partitions, a kind finding no slot holding the rest of its kind, every seed and agent drawing on the pass's `Study.launch_slots`, the cases still tuning (each reads wandb for about 20 s) last, and every seed of a case launched from one `make_train_config` of the pass. The pending watchdog also cancels a CPU-capable case's job pending 30 min for a primary GPU and any job on a CPU fallback partition, and the stuck-job watchdog gives jobs on CPU partitions `CPU_WATCHDOG_SCALE` (4x) its thresholds. Checkpoints move between the devices exactly (the minimal format, x64, the restore template sets the device).
- `orchestration/study.py`: `CaseGridConfig(StudyConfig)` shared base for study configs (working_dir_base, training_datasets, domain_adaptation_methods, target_shot_orders, target_test_set_size or target_test_shots (exactly one), hyperparam_domain_adaptation, hyperparam_num_target_shots, dataset_fractions, num_seeds) and one validator checking every field named in the per-study `FIELD_CHOICES` ClassVar against its allowed values. Each study nests its own `Config(CaseGridConfig)` adding its case axes and study-specific hyperparam fields. Power balance and transport default to unfrozen submodules (freeze_submodules_options=(False,), hyperparam_freeze_submodules=False). `HYPERPARAM_TARGET_SHOTS` also lives in study.py
- `pyproject.toml`: dependencies, build (hatchling), tooling config. popsim, torax and transport-validation-datasets install editable from their submodules (`[tool.uv.sources]`), so a clone needs `git submodule update --init` before `uv sync`. TVD pins disruption-py 0.14.0, and `[tool.uv] override-dependencies` sets numpy to popsim's range over disruption-py's numpy<2 pin
- GPU group: `uv sync --group gpu` for JAX CUDA 13 support

### Data Schema

Every device store holds the shared schema of transport-validation-datasets (`store_schema.STORE_SIGNAL_ATTRS`, every signal with its unit and IMAS ref), IMAS names in SI units on `(shot, time_idx[, rho_tor_norm])` with `time` on `(shot, time_idx)`: `ip`, `b0`, `energy_mhd`, `beta_tor_norm`, `n_e_line_average`, `minor_radius`, `geometric_axis_r`, `elongation`, `triangularity_upper` / `_lower`, `power_ohm`, `power_radiated`, the heating powers `power_nbi` / `power_ic` / `power_lh` / `power_ec`, `r0` on `(shot,)` (the fixed major radius b0 is given at, as IMAS defines b0), the profiles `t_e` / `n_e` with `_error`, `_gradient`, and `_gradient_error` companions (GP or IDA 1-sigma uncertainties on every device), `fresh_profile`, and `fresh_equilibrium` (the grid times a usable reconstruction landed on, the Wmhd and P_oh losses count only those). `get_ds` converts a store to the study's working units with `signals.convert_to_working_units`: any non-SI unit becomes a name suffix (`ip_MA`, `energy_mhd_MJ`, `n_e_line_average_1e20`, `power_ohm_MW`, `t_e_keV`, `n_e_1e20`, ...) the four heating powers sum to `power_additional_MW`, and `b_geo = b0 r0 / geometric_axis_r` is the vacuum field at the geometric axis, which every model uses (TORAX `B_0` at `R_major`, q_star, aB0, the H89 / H98 / P_LH scalings). Every store holds `beta_tor_norm` as IMAS defines it, `100 beta_tor a |b0| / |ip|[MA]` with `beta_tor = 2 mu0 <p> / b0^2` and b0 at r0, built on every device from the reconstruction's own stored energy and volume (TVD `generic.normalized_beta`), so the betan <-> pressure inversions (profile `Inputs.beta` / `te_approx` / `w_approx`, transport `beta_from_energy_mhd` / `beta_tor_norm_from_energy_mhd`) use `b0`, not `b_geo`, and the profile and transport studies carry `b0` alongside `b_geo`. Those inversions call TVD `generic.normalized_beta` / `energy_mhd_from_normalized_beta` (jit-safe, builtin abs) with popsim `calc_plasma_volume` as the volume, since no volume is stored: the round trip recovers the store's betan only up to volume_approx / V_recon (a few percent on C-Mod, ~10 percent on MAST), a known and accepted bias. Power balance inputs are `ip_MA`, `b_geo`, `geometric_axis_r`, `minor_radius`, `elongation`, `n_e_line_average_1e20`, `power_additional_MW`, with `energy_mhd_MJ` the target. The profile and transport preps interpolate the profiles onto the uniform 51-point `RHO_GRID` over `[0, 1]`, and the profile prep adds `t_e_shape` / `n_e_shape` (`PROFILE_SHAPE_VARS`, which the transport prep drops: its sciml profile submodule restores the shape basis fitted in its profile prereq case). The profile prep keeps only `fresh_profile == 1` slices, moved to the front of each shot's time axis in time order (`keep_fresh_timeslices`, the axis cut to the most fresh slices any shot holds, so time_idx counts a shot's fresh slices and the time coordinate keeps their times, about 98 percent of a DIII-D shot's slots are stale), the transport prep is the union of both studies' signals minus `beta_tor_norm`, keeps the forward-filled profile timeslices (contiguous segments matter more than freshness for rollouts, `fresh_profile` rides along as data). Every store is one contiguous 1 kHz segment per shot, so no prep reindexes time, `get_ds` only checks the step. `get_ds` keeps the `max_ds_size` most recent shots of each device, every shot by default (None), and returns the prepared dataset alone.

### Tests

`uv run pytest` runs the fast suite only: `addopts = -m 'not slow'` in pyproject. The `slow` marker covers anything that trains a model, runs a TORAX relaxation, renders comparison figures, or needs real device data (the live device tests now live in the TVD submodule's own suite). Run those with `-m slow` on a GPU node, one suite at a time - concurrent suites OOM the node GPU. Study tests also need the `PTPS_*` env vars from `.vscode/launch.json`, without them they fail with misleading shot-count errors.

On a node without a GPU (like the interactive node), the jax CUDA13 plugin's CUDA library version check hangs forever at the first JAX op, which `popsim.ml` runs at import, so collection never finishes and pytest prints nothing. The root `conftest.py` defaults `JAX_PLATFORMS=cpu` when no `/dev/nvidia*` device exists, which also covers VSCode test discovery. Any other entry point that imports JAX on such a node still needs `JAX_PLATFORMS=cpu` set by hand.

The sample device datasets (`cmod-low1/low2/high.nc`, `mast-low1/low2/high.nc`) are NOT in the repo: `python -m transport_study.datasets.cli sample` writes them from a study store (`datasets/samples.py`, the first, second and last 80 shots in ascending hazard, each read as a device of its own), into the directory `PTPS_TEST_SAMPLE_DIR` names (`/home/zkeith/orcd/scratch/popsim_studies/test_sample_data`, set with the other `PTPS_*` test env in `.vscode/launch.json`, rebuilt 2026-10-14 from the filter_tune cmod and mast stores). Tests that open them read `tests/sample_data.SAMPLE_DIR` and carry `requires_sample_data`, which skips them when the variable is unset, so the variable must be set for the suite to mean anything. Tests that only need a loaded config use `path/to/...` placeholders, and study tests that only build configs use a `tmp_path` working dir so no stale `config_lock.toml` can trip them. Tests that need a real study over data use the session fixture `synthetic_device_stores` (two synthetic TVD stores, cmod and mast, 3 shots each, 30 to 50 steps long). Any path that builds dataloaders there needs `target_test_set_size` >= 2 (popsim rejects a single-shot whole-episode test set), and the time-dep studies' 100-step training segments must be shortened through the public `base_dataloader_config` hook.

Organization rules the suite follows:

- Tests mirror the package layout. Cross-study behavior is tested once in `tests/orchestration/`, not once per study: `test_study_config.py` (config lock, sectioned TOML, parametrized over all three studies), `test_sweep_configs.py` (every sweep yaml of every study, driven off `Case.VALID_MODEL_TYPES`), `test_tables.py` (the generic comparison-table writer), `test_stages.py` (stage segmentation), `test_target_shots.py` (the test cutoff and the three target shot orders, plus a slow test rendering the target_shot_orders figures with each PTPS_DATASET_PATHS store as the target, into PTPS_TEST_WORKING_DIR_BASE/target_shot_orders). Per-study files cover only what actually differs - case naming, the case grid, per-study table specs and plotting. Architecture-level module behavior lives under `tests/modules/<family>/`: `tests/modules/transport_predictor/test_transport_module.py` covers env state seeding, trainable selections, the transformer history buffer, and the TORAX P_aux / absorption wiring, while `tests/transport_transfer/` keeps only study-level wiring.
- Never let a test reach into an underscore-prefixed production name. When coverage needs an internal, the fix is to make the symbol public (that is why `case_coords`, `replace`, `kill_stuck_jobs`, `make_weighted_device_weights`, `shot_stages`, `nn_coefficients`, `build_provider_and_geo` and `transport_coefficients` carry no underscore) or to drive it through its public caller (`_summarize_case_errors` via `collect_results`, `_kill_long_pending_jobs` via `run_unfinished_cases`).
- Orchestration tests drive `StubStudy`/`StubCase` from `tests/stubs.py` via the `make_stub_study` fixture rather than building a real case grid, one seed per case unless a test asks for more (`stubs.with_seed_attrs` stamps a fixture dataset as a seed result). `stubs.mark_analysis_done` stands in for a finished analysis job, and `StubCase(hyperparam=True)` also owns sweep agent jobs.
- `tests/modules/profile_predictor/conftest.py` provides `make_torax_module` and `sample_timeslices`, and TORAX-backed tests must use them instead of re-deriving module kwargs (the sample files are store samples without the `ds_source_idx` organize_data adds, which the fixture fills in). Tests using `sample_timeslices` must carry `requires_sample_data`, and the training smokes build their TrainConfig through a one-case `ProfileStudy` on the samples, never by hand.
- Test modules never import an underscore-prefixed name from the package. When a test needs to reach production internals, either the symbol is public or the test goes through the public path.
- No docstring-only stub tests remain (2026-10-04). A test either pins real behavior or is not written.
