# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Tokamak plasma transport prediction study using POPSIM ML framework. Trains models to predict plasma profiles and power balance on four devices (C-Mod, MAST, DIII-D, TCV) with transfer learning between devices. Three active studies: `profile_transfer` (complete, the template for study structure), `power_balance_transfer` (refactored to match it), and `transport_transfer` (time-dependent profile evolution, reuses machinery from both). `trajectory_optimization` is out of scope (briefly attempted March 2026, inconclusive) - do not extend it.

## Architecture

### Data Flow

```
Device sources
    -> transport-validation-datasets (submodule, builds every device, see its README)
        - C-Mod, MAST: GP fit Thomson (zk), up to <ds>_published.zarr
        - TCV: DEFUSE 0D + raw Thomson, LIUQE GEQDSK, GP fit (zk), up to <ds>_internal.zarr only
        - DIII-D: disruption-py (DISPY EFIT 0D + GEQDSK), IDA GP fits carried over (ida), up to <ds>_internal.zarr only
        - One filter spec and one rho_tor_norm map on all four devices, every stored value causal except the smoothed P_oh and P_rad,
          the TCV n_e fringe-jump correction, and the EFIT and Thomson slices snapped to the nearest grid time (up to 0.5 ms early)
        - power_ohm = Ip V_loop - dW_pol/dt from the GEQDSK block alone on every device (DataWorkflow.add_ohmic_power):
          V_loop = sigma_Bp 2 pi dpsi_boundary/dt at the LCFS, W_pol the psirz integral, no measured flux loop
        - 1 kHz uniform timebase, profiles on rho_tor_norm, IMAS names in SI units
    -> datasets/ wrappers (see datasets/dataset_creation.md)
        - StoreWorkflow selects the study signals of a TVD store into ds.zarr
          (dims: shot, time_idx[, rho_tor_norm], time on (shot, time_idx))
    -> organize_data.py
        - get_ds(source, study_type) converts to working units, adds the hazard metric and runs the per-study prep
        - Per source device a hazard-sorted 80/20 train/val split (the top-hazard fifth is val),
          the target test set and training shots come from target_shots.py (see Domain adaptation below)
        - The training data stays a list of parts (each source's train then val shots, then the target's training shots),
          merged only where it is small (merge_parts: val sets, 0D, the compacted profile view)
    -> trb_utils.segmented_train_dataloader (time-dependent studies)
        - popsim segments each part alone and the segments are merged back into popsim's order,
          so no shot is NaN-padded to another device's length (a DIII-D shot is 20x a MAST one).
          The data is loaded eagerly, so the padding was resident memory (57.5 GB peak in the hs1 debug smoke before the change).
          A room-keeper episode per part reproduces the merged run's tail windows exactly
          (tests/modules/test_segmented_dataloader.py asserts identical samples, order and shuffled batches)
    -> POPSIM module training (submodules/popsim-public/)
        - Input normalization happens INSIDE the modules (see below)
    -> study.py orchestration (cases, W&B sweeps, SLURM)
    -> analysis / plotting
```

### Key Abstractions

**Study/Case pattern** (`orchestration/study.py`): A `Study` holds many `Case` objects. Each case is a unique combination of case-grid axes (e.g. `model_type x training_data x normalization x domain_adaptation x freeze x num_target_shots`). Cases support prerequisites (chained dependencies, e.g. a transfer case depends on its transfer_pretrain twin, and the power balance sciml-taue-nn / sciml-taue-scalinglaw model types depend on p_oh / p_rad submodule cases). `ProfileStudy` (`profile_transfer/profile_study.py`) is the reference implementation, `PowerBalanceStudy` (`power_balance_transfer/power_balance_study.py`) and `TransportStudy` (`transport_transfer/transport_transfer_study.py`) mirror it. TransportStudy's sciml prereq chain is two deep: sciml -> power_balance + profile pseudo-model-type cases (trained with the OTHER studies' TRBs and study types, variants picked by the `power_balance_model_type` / `profile_model_type` config fields), and power_balance -> p_oh + p_rad.

The `Study` base provides everything generic, subclasses only declare what differs:

- Base `Study.Case` (dataclass): common fields (`model_type`, `training_data`, `domain_adaptation`, `num_target_shots` (>= 0), `target_shot_order`, `prereqs`), validation, prereq building (`[hyperparam case, model_type_prereqs(), transfer pretrain case]` deduped in order), `replace` (rebuild through the real constructor), hyperparam-case logic driven by `HYPERPARAM_FIELDS` (each maps to a `config.hyperparam_<name>` attribute), token-driven `__str__` (`case.{mt}.td_{td}` + `STR_TOKEN_FIELDS` tokens + `targ_{n}` when da or exnihilo + `order_{o}` unless the base ascending order + `da_{da}`, the freeze tokens of all three studies suppressed at False so only frozen cases carry `freeze_True`, likewise the `mo_` token of power balance and transport so only multiobjective cases carry `mo_True`), and `__hash__` (all fields except prereqs).
- Subclass `Case` is thin: extra fields (`data_normalization` and `freeze_shapes` for profile, `data_normalization`, `freeze_submodules` and `multiobjective` for power balance, `freeze_submodules`, `geometry_builder`, `torax_state` and `multiobjective` for transport), the three ClassVars (`VALID_MODEL_TYPES`, `STR_TOKEN_FIELDS`, `HYPERPARAM_FIELDS`), `normalization_method()` (the method the case trains with, which decides its transfer twin), `pin_inapplicable_axes(fields)` (calls the base, which pins the target shot order to ascending at 0 target shots, then pins the axes a model type ignores, freeze to the hyperparam_freeze_* value, multiobjective to hyperparam_multiobjective outside each study's `MULTIOBJECTIVE_MODEL_TYPES` and geometry / torax_state to circular / rebuild), and an `__init__` that sets the extra fields then calls `init_common`. TWO DATACLASS TRAPS: the subclass body must keep its own `__init__` (or `@dataclass` regenerates one, silently dropping validation and prereq building) and must alias `__hash__ = Study.Case.__hash__` (or `@dataclass` with eq=True sets `__hash__ = None`).
- `make_train_config` is a template method: base builds the shared scaffold (dataloader/loss/optimizer bases, the weighted `device_weights` and the per-device `chi_sigma_floors` injected into the loss config, which the val suite aliases, transfer checkpoint wiring via `_set_transfer_checkpoint`, tuned-config merge, the study's training steps per epoch, then `_scale_transfer_lr` AFTER the merge so swept configs cannot overwrite it). Subclass hooks: `base_dataloader_config(case)` (spreads the base `target_split_config(case)`: training data, da and the `TargetSplit` fields), `base_loss_config()`, `base_optimizer_config()` (profile and transport add grad clipping), `model_train_spec(case, dataloader_config_base) -> ModelTrainSpec` (per-model-type train_run_builder + dataloader + model_init dicts), `tuned_model_init_updates(case, tuned_config)`. The tuned-config merge indexes `TUNED_DATALOADER_KEYS` and `TUNED_LOSS_KEYS` strictly (KeyError when a tuned config lacks one) and replaces the optimizer_config wholesale. The power balance and transport studies' `_make_submodule_config` recurses through `make_train_config`, so submodule configs get their own tuned merge and transfer wiring.
- **Fixed steps per epoch** (`Study.steps_per_epoch`): every case trains the same optimizer steps per epoch at its unchanged batch size, so the LR schedule (`len(train_dl) x max_epochs`), the validation cadence and the patience count the same steps whatever the case's training set (exnihilo vs historic is a data comparison, not a step-budget one). steps_per_epoch is the natural steps per epoch of the largest training set the LOCKED fields allow (every non-target device's train and val shots plus the whole target pool `target_pool_size`, as addition), measured on the case's final loader config after the tuned merge, so each loader family (PB top-level, p_oh / p_rad, profile, the transport pseudo-types) gets its own and none follows the case grid or the study of a lineage. `make_train_config` injects it as `dataloader_config["steps_per_epoch"]`, and the TRBs wrap their train loader in `trb_utils.FixedStepsDataLoader`, which chains reshuffled passes of a smaller set up to it. A measurement loads every device (about 3.5 min and 60 GB per transport top-level family in production), so it is recorded in the working dir's `steps_per_epoch.toml` by loader-config hash, read back root-most study of the lineage first (a child trains with its borrowed cases' value), and deleted whenever a fresh config lock is written, so a cleaned study measures again. hs1 production: PB 17 (p_oh / p_rad 841), profile 122, transport 126. No sweep may change `dataloader_config` (test_sweep_configs).
- `make_cases(cfg)` is generic: the product over the Config's case axes (`CaseAxis` fields, each naming the Case field it feeds), the shared da None / target-shot skip rule, `Case.pin_inapplicable_axes`, then `finalize_cases` (unwrap prereqs, dedupe, sort, drop impossible). cfg is an argument so another config's grid can be rebuilt.
- `run_study` is a base classmethod (Fire CLI reads its signature, so flags live in one place): config TOML parse via `cls.Config`, `clean_working_dir` (clean_models / clean_results / clean_figures, BEFORE the Study is built so a study whose lock refuses the config can still be reset), Study init (config lock), `record_case_grid`, `setup_directories` (clean_sweeps, mkdirs), partition check, `_visualize_data()` (uses the `DATA_VISUALIZATION` ClassVar), orchestration loop + `collect_results` + write `collected_results.nc` (skipped if it exists), then `run_analysis(enable_parallelism)`. Each study module's `fire.Fire` main maps `run_study` and `reset_study` straight to its class's classmethods. `reset_study` starts a study over: it refuses while any job of the study is queued on any partition, deletes the whole working dir and the wandb sweeps of the study's own hyperparam cases, then writes a fresh config lock. A lineage resets root-first, so every child's lock records its parent's fresh stamp before any orchestrator starts (`studies/hs1/power_balance/launch_hs1_pb.sh` resets and submits the power balance chain). The run_study clean flags refuse to run with parallelism, so the reset is the way to start a parallel study over.
- **Sweep trials preempt and resume** (popsim `launch.finish_sweep_run`): a trial cut by the wall budget marks itself preempting and finishes with exit code 1, so wandb holds it out of the bayes fit and requeues it, and the next agent resumes it under the same run id from `Study.sweep_checkpoint_dir(case)/<run id>` (`launch_sweep` sets `resume` and the root, popsim's `_run_train` nests the run id and inits with `resume="allow"`). So every trial trains to its max epochs or patience whatever device and job length it ran on, and a preempted trial stays outstanding in `get_completed_runs`. `_finalize_sweep` and clean_sweeps delete those checkpoints. The patience count (popsim `EarlyStopping.state()`) is saved in every checkpoint's metadata and restored on resume, strictly: a checkpoint without it raises.
- **Top-K results** (`orchestration/topk_results.py`): production runs keep the `num_result_checkpoints` best-by-val-loss checkpoints, and the result file keeps every error variable of each of them on a `ckpt` dim (coord the epochs, attr `result_checkpoint_best_epoch`, float32), while the pred / targ variables are the best checkpoint's, a length-1 ckpt dim at K = 1. Every case score is computed per checkpoint and reduced by `topk_statistics` to three values: `<name>` the top-K mean, `<name>_best` the best checkpoint's and `<name>_ckpt_std` the std over the K checkpoint scores (the noise floor between cases). Comparison figures plot the top-K mean with the top-K std as the error bar, tables carry all three for the headline metric, and case reports rank and title by the best checkpoint, whose predictions they plot.
- `collect_results` schemas intentionally differ: the base implementation emits the per-case scalar summary (dims: case_idx) via `_summarize_case_errors` (each statistic per checkpoint, then `topk_statistics`), which power balance and transport both inherit unchanged, and profile overrides it with a per-shot long-form dataset (dims: record, top-K means). All use the base `case_coords` driven by `case_coord_names()` (case_idx plus the case-axis Case fields).
- `run_analysis`: power balance and transport call `orchestration/case_analysis.run_summary_analysis(study, enable_parallelism, LAYOUT, COMPARISON_FAMILIES, TABLE_SPEC)` (transport with `figures_from_metrics=True`, so its figures are the stage grid of `collected_metrics.nc` like the profile study's, power balance's the 2x2 grid of `collected_results.nc`), profile runs the same steps itself plus its freeze-shapes and TORAX relaxation figures. With parallelism the per-case analysis (stage metrics + case report) fans out as one SLURM CPU job per case (`run_case_analysis_parallel`), and the serial paths afterwards skip finished cases. Each study names its own pieces in two ClassVars that `orchestration/case_metrics.py` and `orchestration/case_reports.py` resolve with import_module: `ANALYSIS_METRICS_MODULE` exports `METRIC_NAMES` and `case_timeslice_metrics(study, case, result_ds)` (a `StagedTimesliceMetrics` record per valid test timeslice, one column per retained checkpoint, `best(name)` the best checkpoint's), `ANALYSIS_REPORTS_MODULE` exports `case_report_done(case_dir)` and `render_case_report(result_ds, ts_metrics, case_dir)`. The shared side holds `staged_result_records` (the per-shot read of a result file every metrics module uses: the nearest-time join, the stage labels from `stages.segment_stages`, the records of every clock-advancing timeslice with a target), the per-stage aggregation (each stat per checkpoint, then `topk_statistics`), the per-case `case_metrics.nc` caches combined into `collected_metrics.nc` (`collect_metrics`), and `best_worst_pdf`. Every test suite writes `error_diverged_ts` (1 where the prediction went non-finite, 0 where finite, NaN without a target, outside the freshness mask like the validation divergence penalty) and NaN instead of any non-finite error, so a blow-up stays a record whose errors the means skip, and every study reports the diverged fraction (`diverged_mean`, a table column, also a transport figure row). The profile and transport studies score the validation chi itself: the shared `ProfilePredictorTRB.make_test_eval_suite` writes `error_chi_value_ts`, `error_chi_grad_ts` and `error_chi_ts` (value + `gradient_weight` x gradient, the per-timeslice validation loss less the device weight, fresh-masked in the transport study) from the `loss_config` its `test_eval_suite_config` shares with the val suite. The transport study's own metrics module adds that chi (headline `combined`) to the power balance abs / rel / diverged metrics, NaN chi for the scalar prereq cases, and its reports rank its profile results by time-averaged chi, each page only the chi traces over the shot (the predicted profile maps took most of the rendering time, about 13 minutes per case), and render scalar prereq result files with the power balance page. Comparison figures come from `orchestration/comparison_figures.comparison_figures(ds, layout, family, figure_dir)`: each study's plotting.py declares a `ComparisonLayout` (panel rows and columns, the per-panel stats, the case-grid fields with their filename tokens) and its `COMPARISON_FAMILIES` (a line per value of one field, a figure per combination of the rest, `min_series=2` for the families only a child study varies: target_shot_order, freeze_submodules, multiobjective). exnihilo only exists without adaptation, so `ComparisonFamily.include_exnihilo` (set on every training_dataset_comparison) also draws the exnihilo cases in the figures that fix another domain_adaptation, beside the historic sets' adapted ladders. The shared `TD_LABELS` / `TD_COLORS`, `FREEZE_*` and `MULTIOBJECTIVE_*` maps live in comparison_figures.py. Each study's tables.py declares a `ComparisonTableSpec`, and the writer plus the shared power balance / transport per-case frame live in `orchestration/tables.py`. Power balance per-shot errors in result files are raw time integrals (long shots score worse), so its study_metrics and case_reports rank shots by TIME-AVERAGED error instead (`shot_time_averaged`).
- Other subclass ClassVars: `SWEEP_CONFIG_DIR`, `STUDY_TYPE`, `DATA_VISUALIZATION`, `CHI_VALIDATION_LOSS` (profile and transport, injects `chi_sigma_floors`), `TUNED_DATALOADER_KEYS` / `TUNED_LOSS_KEYS`.

**Hyperscrabble (parent studies)** (`orchestration/lineage.py`): a study may name a `parent_study` of the same type under the same working_dir_base, and borrows read-only every case an ancestor has trained or whose current grid (as the ancestor's config lock records it) will train. So a secondary study along a restricted axis trains only its new cases, e.g. a frozen-vs-unfrozen comparison on one normalization and one da trains only the frozen cases and borrows the rest, hyperparam and submodule prereq cases included. Chains recurse (tertiary -> secondary -> primary).
- A child refuses to start unless every LOCKED field equals each ancestor's (a borrowed case is only the same model under the same setup).
- Ownership is root-first: `Study.case_home(case)` is the root-most ancestor that claims the case, else the study itself, so every study of the chain agrees where a case lives and a borrowed case is never rebuilt around another study's prereqs. A nearer study holding its own copy of a case an ancestor now claims (the ancestor's grid grew) raises instead of mixing.
- `trained_model_dir`, `result_path` and `tuned_config_path` route through `case_home`, which covers every cross-case read (tuned configs, transfer checkpoints, the submodule checkpoint_dir nested in a TrainConfig, analysis). launch_train / launch_sweep / the tuned-config writes call `_require_local`, `run_unfinished_cases` only waits on borrowed cases ("waiting on <ancestor>"), the watchdogs and clean_sweeps see local cases only, and `trb_utils.restore_from_checkpoint` raises on a missing dir instead of letting the checkpoint manager create one in an ancestor.
- Freshness is transitive: each lock records its parent's stamp at creation, `refresh_lineage` reloads the chain every orchestration pass, and a reset ancestor (clean_models / clean_results) stops every descendant until it is cleaned too.
- Analysis stays local: `case_metrics.nc` lives in the study's own result dir (a borrowed case reads its home's cache when present), borrowed cases get no case report (their home renders it), figures, tables and collected results cover the whole grid.

CRITICAL: `str(case)` names checkpoint dirs, result files, tuned-config paths, wandb projects, and SLURM job names - byte-level drift orphans existing runs. `restore_predictor.checkpoint_to_profile_case` parses case-directory names back into Cases and must stay in sync with `__str__`. `Study.case_by_name` finds a case of the study by that string (the analysis jobs and `plot_torax_evolution` use it). Each study's `tests/<study>/test_*_case_naming.py` pins the literal case strings.

**TRB pattern and shared helpers** (`modules/trb_utils.py`, `modules/power_balance/scalar_power_trb.py`): TrainRunBuilders share `trapezoid_dropna` / `integrate_error_over_time` (per-shot NaN-safe time integrals of error), `make_exponential_adamw` and `make_grouped_exponential_adamw` (the standard optimizer and its per-submodule learning-rate variant: lr0 falls by `decay_rate` every `transition_steps` and holds at lr0 x `lrf_frac`, the sweeps pin decay_rate at 0.1 and swept `transition_frac` alone sets the decay speed, and `no_decay_names` exempts pytree paths from the weight decay), `make_loss_eval_suite` (validation loss mean + a <=100-point subsampled loss vector for wandb, a fresh jitted closure per suite so eqx.filter_jit caches never collide across cases), `resolve_case_datasets` (per-case dataset selection and prep shared by EVERY study TRB), `normalizer_fit_dataset` / `attach_normalizer_fit_ds` (the transfer_pretrain normalizer-fit dataset rides on `train_dl.normalizer_fit_ds`), `target_device_idx` (the CORAL reference), `restore_from_checkpoint` / `submodule_config_dict` (submodule and transfer restores), `scalar_study_results` (the power balance and p_oh / p_rad test suites, relative errors against |target| plus the per-signal `SCALAR_REL_ERROR_FLOORS`), the chi helpers (`chi_value`, `chi_gradient`, `chi_sigma_floors`, see Profile loss split), and `get_time_dep_dataloaders` + `mask_to_largest_contiguous_segment` (the segment-based time-dependent dataloaders, parameterized only by study_type, training through `segmented_train_dataloader` on the parts `resolve_case_datasets` returns, each prepared by `prepared_for_dataloader`, the train loader then wrapped by `fixed_steps_train_dataloader` at the study's steps per epoch), and `huber_profile_loss` / `chi_profile_loss` (one profile channel's training and validation loss, shared by the profile and transport TRBs). The power balance and transport TRBs delegate to `get_time_dep_dataloaders`, the profile TRB builds its time-independent dataloaders on `resolve_case_datasets` directly. `ScalarPowerTRB` is the shared base for the p_oh / p_rad predictors - `OhmicPowerTRB` / `RadiatedPowerTRB` only set the `SIGNAL` and `MODULE_CLS` ClassVars, and sweep configs reference them by their dotted paths. Like every study's, its validation loss reads no swept huber delta. `TransportPredictorTRB` reuses `ProfilePredictorTRB.make_test_eval_suite` with `fresh_only=True`, so forward-filled timeslices score NaN and drop out of every error and shot integral.

**Dataset creation** (`datasets/`, transport-validation-datasets): every device is built by the transport-validation-datasets (TVD) submodule, a `DataWorkflow` subclass per device in its `machine/` (cmod, mast, tcv, d3d): source pull and the one filter spec (`filters.py`), profile fits (GP fit of the Thomson channels by the `zk` method, dispatched to ORCD, or for DIII-D the `ida` method that carries IDA's own GP fits onto the fit grid, refused on any other device through `DataWorkflow.fit_methods`), the full GEQDSK block on every device, and the stack into `<ds>_internal.zarr`. TCV and DIII-D are `publishable = False` (no release permission): TVD stops them at the internal store, refusing publish and the IMAS export. Device specifics (DIII-D DISPY EFIT and IDA databases, TCV DEFUSE readers and LIUQE-to-GEQDSK conversion, filter thresholds, known limitations) are documented in the TVD README, not here. This repo's `datasets/` is wrappers only: `workflow.StoreWorkflow` is a lazy xarray pass over a TVD store (published for C-Mod and MAST, internal for TCV and DIII-D) that keeps `signals.STUDY_STORE_SIGNALS` (the shared schema less `fresh_equilibrium`, which no study reads), trims the trailing NaN padding to the longest shot, refuses a windowed store, and writes `ds.zarr` through TVD's chunked writer with diagnostic plots (`plotting.py`), no popsim or JAX import. TVD keeps the source signs of ip and b0 (the per-shot `cocos` records the convention) and `signals.convert_to_working_units` takes the magnitudes on every load. The CLI has one `build` subcommand taking the device name, and `d3d_dataset.INNER_WALL` stays for the out-of-scope trajectory modules.

**Input normalization as POPSIM modules** (`modules/normalization.py`): the power-balance models take the same 7 physical inputs (`ip_MA, b_geo, geometric_axis_r, minor_radius, elongation, n_e_line_average_1e20, power_additional_MW`) plus `ds_source_idx`. Each model owns an `InputNormalizer` (`raw` identity, `physics` dimensionless, `zscore` per-device, `coral` per-device covariance alignment, and the `physics-coral` / `physics-zscore` stat stages fitted in the physics feature space, whose classes subclass the plain ones and only swap the `features` hook), fitted from TRAINING data only at model_init and stored as frozen buffers (they checkpoint with the model but are never trainable - trainable selectors pick `module.nn` leaves explicitly). CORAL (`fit_coral_stats`) aligns every device's covariance to the TARGET device's: the target keeps the identity transform and needs only 1 complete shot, a source device needs `MIN_CORAL_SHOTS` shots or keeps the identity, and features without target spread or with degenerate device spread keep identity slots. CORAL is therefore a no-op when the fit data holds no target shots (hyperparam, targ_0) or only target shots (exnihilo), and acts in weighted / addition / transfer cases from 1 target shot. The profile and transport studies' counterparts are `profile_predictor/module.make_nn_input_normalizer` (10 dimensionless `nn_inputs`) and `transport_predictor/module.make_transport_nn_input_normalizer` (those 10 slots from the measured Wtot plus `paux_norm`), thin wrappers over the shared `normalization.make_feature_normalizer` + `feature_fit_arrays` (feature matrices built with `flat_columns`), which hold the one method dispatch (`physics` identity / `physics-coral` / `physics-zscore`, `FEATURE_NORMALIZATIONS`). They share the contract of `make_normalizer`: fit data `None` yields identity buffers with the checkpoint's pytree structure. All three studies' TRBs pick the fit dataset through `trb_utils.normalizer_fit_dataset` (skipped entirely when a transfer checkpoint will overwrite the buffers), pass `trb_utils.target_device_idx()`, and index `data_normalization` strictly. `organize_data.normalize_domain` implements the same math on one combined dataset for data visualization only, with `feature_space` selecting which family's features the physics* methods run on (`power_balance` = the 7 `physics_feature_vec` slots, `profile` = the 10 `nn_inputs`, `transport` = the 11 transport features).

**Data visualization** (`orchestration/data_visualization.py`): `DataVisualizationBase` holds the shared hazard-extrapolation, target-shot-order (the shots each configured order picks at each positive shot count, in the hazard plane and P_aux vs Wtot) and domain-overlap plotting, and each study's `data_visualization.py` is a thin subclass setting `STUDY_TYPE`, `VAR_GROUPS` (variable pairs per normalization method), and `FEATURE_SPACE` when its models do not consume the power-balance inputs (profile_transfer sets `"profile"`, transport_transfer `"transport"`, so their physics* plots show the features those modules actually normalize). The combined every-device dataset of the domain-overlap plots keeps only the variables off the radial grid, since the plots read 0D signals and padding every device's profiles to the longest device takes tens of GB. Shared dark-theme figure styling (colors, font sizes, `LEGEND_STYLE`, `style_axis`) lives in `transport_study/plot_style.py`.

**Module pattern**: Predictors inherit from POPSIM's `TimeIndepModule`/`TimeDepModule`. Profile predictor (time-indep) predicts Te/ne on a uniform 51-point `rho` grid over `[0, 1]` (not psi_n). Model families: `shape-init-pca` / `shape-init-kmeans` (point shapes from an uncentered PCA or k-means of the unit-integral training profiles, weighted by an NN, shapes optionally frozen), `mlp`, `reservoir`, and `torax-constant` / `torax-gyrobohm` / `torax-qlknn` (differentiable TORAX simulation with NN-predicted transport/edge/source parameters, `torax-cgm` was cut on 2026-10-01). The shared `TORAX_CONFIG_BASE` (profile `train_configs.py`) sets Z_eff 1.5 over TORAX's default neon impurity and holds no impurity line radiation, no cyclotron radiation and no `generic_current` (TORAX's default drives 20 percent of Ip at rho 0.4), and `torax_module.clamp_core_profiles` clips the evolving profiles after every solver step, an exact identity in range so nothing drifts per step (a softplus clamp there removed 2-27 eV per call until October 2026). The profile relaxation keeps the base solver, one linear step with Pereverzev at the TORAX defaults, whose progress per step does not depend on dt, so its output is N damped steps from the parabolic initial profiles rather than a steady state. The step is fixed at `trb.RELAXATION_DT_S` = 25 ms and `n_solver_steps` (default 8, swept over 4 / 6 / 8) is the only window knob, `trb.relaxation_numerics` turns it into the TORAX numerics. Every TORAX network predicts dimensionless values that the shared bound functions turn into TORAX units: the density pinch as the peaking rate c = V a / D (`density_peaking_rate`, d ln n / d rho_norm in a source-free steady state, so one range means the same peaking on every device, `bound_transport_coefficients` takes the minor radius), the constant model's chi_i / chi_e / D_e as multiples of chi_ref = a^2 / (5.8 `TAU_REF_S`), the BGB and QLKNN knobs as multipliers, the fueling and heating as multiples of nebar x volume_approx / `TAU_REF_S` and w_approx / `TAU_REF_S` (`TAU_REF_S` = 50 ms in torax_module), and the edge BCs as fractions of nebar and te_approx. Every family builds its Outputs with `profile_outputs`, and the shape-init, MLP and reservoir families share the decode `assemble_profile_outputs` over `scaled_profile_points` (ne points, te points, then a te and an ne scale correction that multiply them). These purely data-driven families see only the normalized features: no n_e_line_average or te_approx scale enters their outputs. torax-* model types additionally carry a `geometry_builder` case axis (`circular` or `miller`, see `torax_module.build_circular_geometry_jax` / `build_miller_geometry_jax`). The circular builder is TORAX's own model: it labels surfaces by the midplane radius and its q carries TORAX's 1.25 correction. The miller builder labels them by the normalized toroidal flux radius the data is stored on, inverting it from the vacuum toroidal flux of each Miller contour, and its CHEASE geometry type leaves q uncorrected. Its shape profiles come through the coefficient dict (`geometry_shape_coefficients`, closures in `miller_shape_coefficients` for now): the magnetic axis keeps 0.7 of the LCFS elongation excess, and the axis Shafranov shift is (a / 2R)(beta_p + l_i / 2) of the minor radius with l_i 0.8, capped at 0.3 a. No default is suppressed from `str(case)` for this axis (every case gets an explicit `geom_` token), and it is deliberately NOT a `HYPERPARAM_FIELDS` entry so `miller` cases get their own hyperparameter sweep and tuned config instead of inheriting circular's. Power balance (time-dep, simple-Euler stepper, `energy_mhd_MJ` state) predicts stored-energy evolution with five architectures: `sciml-taue-scalinglaw` (H89/H98 tau_e blend gated by a P_LH scaling, consumes PHYSICAL units, prefactors trained as their logs and every coefficient exempt from weight decay via `SCALING_LAW_FIELDS`, called `scaling_law` before July 2026), `sciml-taue-nn` (bounded NN tau_e, called `sciml` before July 2026), both on the shared `PowerBalanceTaue` step dW/dt = P_aux + P_oh - P_rad - Wtot/tau_e with only `predict_taue` differing, `mlp` (`PowerBalanceMLP`, an MLP predicts dW/dt from the normalized inputs and its own predicted Wtot, the feedback that keeps the rollout from being an open-loop integrator. Its normalizer, like the transformer's (`MODEL_TYPES_WITH_ENERGY_INPUT`), is built `with_energy`: Wtot is an 8th slot (MJ for raw / coral, beta_N with b_geo for the physics methods, per-device z-scored for the zscore methods, inside the CORAL alignment for coral) and `energy_rate_scale` maps the NN output back to dW/dt (MW for raw / coral, the normalized energy unit per `TAU_REF_S` = 30 ms otherwise), so both sides sit near 1. Called `unstructured_nn` before July 2026), and `transformer` (recurrent causal attention: a rolling buffer of the past PREDICTED Wtot values is carried in the module State as a discrete `discrete_no_save_field`, seeded with the measured t0 Wtot tiled, and the embedded-input query attends over embedded Wtot tokens plus a learned per-slot position embedding, needed because scalar tokens are otherwise permutation-invariant - see `popsim/modules/delay.py` for the discrete-state pattern. Every buffered Wtot goes through the normalizer's energy slot at the current inputs and the head output through `energy_rate_scale`, as in the mlp), and its `multiobjective` case axis (`MULTIOBJECTIVE_MODEL_TYPES = ("transformer",)`, a `HYPERPARAM_FIELDS` entry so a multiobjective case tunes on the plain transformer's sweep, called the `transformer-multiobjective` model type until October 2026): `PowerBalanceTransformer` with `predicts_powers` has two more head outputs predicting P_oh and P_rad on the `energy_rate_scale` power scale, never fed into the Wtot update, and its target_vars carry the measured powers so the sciml anchor terms train them, multi-objective learning compared against the plain transformer in hs1_pb_multiobjective). `sciml-taue-scalinglaw` and `sciml-taue-nn` hold `p_oh` / `p_rad` submodule predictors trained as their own prereq cases and restored from checkpoints. During joint training the loss anchors the submodule predictions to the measured `power_ohm_MW` / `power_radiated_MW` targets (`anchor_weight_power_ohm` / `anchor_weight_power_radiated` loss keys, 2e-3 so they match the Wtot term of a trained model instead of swamping it, training loss only so `val/loss.mean` stays pure Wtot, no-op for cases whose target_vars lack the powers, a multiobjective transformer's power heads get the same anchors) and the optimizer runs the submodules at a reduced learning rate (`submodule_lr_factors` in the power balance `base_optimizer_config`, default 0.1x, applied by pytree-path labeling in `trb_utils.make_grouped_exponential_adamw` via optax multi_transform). Transport predictor (time-dep, simple-Euler stepper, `modules/transport_predictor/`) predicts ne/te profile EVOLUTION on the same rho grid from the power-balance inputs plus triangularities (no measured betan - beta quantities derive from the evolving state Wtot): `transformer` (rolling profile-history buffer as discrete state, same shape as the power balance transformer: current-feature query attends over position-embedded profile tokens, each a peak-normalized history row plus its ne and te peaks - only predicted profiles are kept as history, never past input features, and the next profiles come out of the same `scaled_profile_points` decode with no n_e_line_average or te_approx scale. A multiobjective transformer has two more head outputs after the decode's rows (the decode reads its corrections at negative indices, so the head output is sliced first): the stored energy as W_p (1 + nn) over the profile-implied W_p and the ohmic power as W_p / `TAU_REF_S` nn, never fed back into the profiles), `sciml` (composes a trained PowerBalance for the Wtot state and a trained ProfilePredictor fed the state-implied betan, its Output surfaces `energy_mhd_MJ_pred` / `power_ohm_MW_pred` / `power_radiated_MW_pred` so the training loss can anchor them to the measured signals - `anchor_weight_energy_mhd` / `anchor_weight_power_ohm` / `anchor_weight_power_radiated` loss keys, training loss only, no-op for the cases whose target_vars lack the signals (all but sciml and the multiobjective ones) - and the optimizer runs the whole power_balance subtree at a reduced learning rate via `submodule_lr_factors` while the profile predictor keeps the full schedule, same `make_grouped_exponential_adamw` mechanism as the power balance study), and `torax-*` (one TORAX solver step of the 1 ms dataset timebase per call, config from `transport_predictor/train_configs.make_transport_torax_config`, whose solver comes from `TRANSPORT_SOLVER_BLOCKS`: one corrector iteration, without Pereverzev for constant / gyrobohm and with it for qlknn (each iteration costs about one more full step), since a corrector-free step solves n dT/dt instead of d(nT)/dt at any dt and the default Pereverzev damps shape changes by ~dt chi / a^2. the rebuild config does not evolve psi within the step since it re-derives psi from Ip every step, the carry config does. The transport config also turns on Angioni-Sauter neoclassical transport, neoclassical chi, D and V with the Ware pinch at about 1.1x per step, which the profile relaxation leaves off). Every torax-* Output also carries TORAX's own stored energy (`W_thermal_total`, ions at T_i, no fast ions) and ohmic power (`P_ohmic_e`, j_ohm E over the Sauter resistivity at the state's T_e and Z_eff) from the post-processed outputs of the seeded state at the reported time (`TransportPredictorToraxBase.inferred_outputs`), which only a multiobjective case anchors. There is no P_rad output: TORAX's core radiation is 2-10 percent of the measured DIII-D P_rad at any plausible Z_eff (divertor and edge radiation dominate), so Mavrin impurity radiation stays off. Unlike the profile study's TORAX modules, which infer the heating magnitude with an NN, the transport ones feed the MEASURED `power_additional_MW` straight to `sources.generic_heat.P_total` and let the sources network predict only the deposition shape, the gas-puff fueling, and `absorption_fraction = 1 - exp(-softplus(nn) * n_e_line_average_1e20 * a)` - a Beer-Lambert shine-through form over the line-integrated density that is always in (0, 1) and never gradient-dead at saturation. The profile modules keep the fixed config absorption of 0.9, where it would be degenerate with their NN-predicted `P_total`. torax-* carry both the `geometry_builder` axis and a `torax_state` axis ("rebuild", `TransportPredictorTorax`, re-seeds TORAX from stored ne/te each step with T_i := T_e and psi from Ip, "carry", `TransportPredictorToraxCarry`, also keeps T_i and psi as plain cell-grid arrays and re-enters them each step through `initial_psi_mode` "profile_conditions" with the current evolving, which reproduces TORAX's own continued evolution to machine precision. A carried TORAX `SimState` pytree crashes every popsim state partition, `CellVariable` rejects the None-filled halves, so no TORAX pytree may enter a module State). In this study (unlike profile_transfer) both axes' defaults ("circular", "rebuild") are suppressed from `str(case)`, and neither is a `HYPERPARAM_FIELDS` entry. The transport `multiobjective` case axis (`MULTIOBJECTIVE_MODEL_TYPES` = transformer and torax-*, a `HYPERPARAM_FIELDS` entry so a multiobjective case tunes on the plain case's sweep, sciml pinned since it always anchors) puts `MULTIOBJECTIVE_TARGET_VARS` (energy_mhd_MJ, power_ohm_MW) into target_vars so the existing anchor terms train them, while every top-level case loads the measured powers (as extra_vars when not anchored) so all train on the same segments. Normalization is not a case axis in the transport study (unlike profile, where it is): a study-wide `data_normalization` config field ("physics", "physics-coral", or "physics-zscore") controls the per-device stat stage (`CoralFeatureNormalizer` / `ZScoreFeatureNormalizer`) over the 11 transport features. `TransportPredictorEnv` (in module.py) seeds each architecture's state from the measured t0 signals carried in the dataloader's state_vars.

**Profile loss split** (`profile_predictor/trb.py`, mirrored in `transport_predictor/trb.py`): the training and validation losses must stay different. Training (`get_loss_fn`) is huber on the peak-normalized residual of the values and of the GP-fit gradients (the gradient term masked to rho below `GRAD_RHO_MAX` = 0.9, one cut shared by the training losses, the validation chi and the analysis chi, beyond which the GP fits extrapolate into the pedestal), with the swept `huber_delta` / `huber_delta_grad`, and never reads the error bars. Validation (`get_val_loss_fn`, the sweep metric `val/loss.mean` and the checkpoint selection) is chi, the residual in units of the GP-fit error bar (`trb_utils.chi_value` / `chi_gradient`, the gradient term masked to rho below the same `GRAD_RHO_MAX` and weighted by `gradient_weight`). Each error bar is floored per device and channel at `chi_sigma_floors`, the `CHI_SIGMA_FLOOR_PERCENTILE` percentile of that device's positive peak-normalized fresh error bars (`trb_utils.chi_sigma_floors`), which `make_train_config` injects into the loss config of every `CHI_VALIDATION_LOSS` study. Chi reads no huber delta, so no swept delta can game the sweep metric. The test suite writes the same chi per test timeslice and retained checkpoint, which `profile_transfer/study_metrics.py` reads back. The transport losses use the same per-channel terms (`trb_utils.huber_profile_loss` / `chi_profile_loss`, so its target_vars carry the GP-fit gradients and their error bars, NaN exactly where the values are on every device) and add a freshness mask: the value and gradient terms are multiplied by the `fresh_profile` target var so forward-filled timeslices steer neither training nor checkpoint selection, the anchor terms stay unmasked (their signals are measured at every timeslice) and training only, training averages the two channels where chi sums them, and a non-finite rollout is charged `divergence_penalty` in training and the chi-scale `divergence_penalty_val` in validation. The transport top-level sweeps tune `huber_delta_grad` like the profile study's.

**Domain adaptation / transfer modes** (`domain_adaptation`): `none` (train and test on the same device(s), baseline and hyperparam case), `weighted` (add a small amount of highly-weighted target data during training, weights from `Study.make_weighted_device_weights`, called `mixing` before July 2026, so old run artifacts may carry the name), `addition` (add target shots to the training set as normal samples, no weighting - identical datasets to `weighted`, differs only in the absence of `device_weights`), `transfer` (pretrain through the `transfer_pretrain` twin, restore its checkpoint, fine-tune the last layers on the target). The twin (`Study.Case.transfer_pretrain_case`) trains on historic data with checkpoint selection on the target test set. A stat normalization fits its statistics on historic + the case's n target shots, so its twin keeps n, while the stateless ones (raw, physics) share one twin at `HYPERPARAM_TARGET_SHOTS`. The finetune learning rate is step-budgeted (`transfer_lr_scale`: lr0 times 1 / steps_per_epoch clipped to [`TRANSFER_LR_FLOOR`, 1], on a flat schedule, so with the fixed steps per epoch every finetune runs near the floor, accepted 2026-10-06 and due to be re-tooled). The `exnihilo` training-data option trains from scratch on the target device only. The target split lives in `orchestration/target_shots.py` and is decided on the POWER BALANCE view of the target device in every study, so a transport case and its power balance and profile prereqs train and test on the same shots (`organize_data._split_target_shots` then indexes the study's own view by shot number and raises if its prep dropped one). The test set is never trained on (num_target_shots = -1, the old all-shots cheating reference, was removed in October 2026): exactly one of `target_test_set_size` (the highest-hazard shots) or `target_test_shots` (every shot at or above the hazard rank of the lowest named shot) defines it. Hazard = per-shot p95 of normalized (energy_mhd_MJ^2 + ip_MA^2)^0.5, called "performance" before July 2026, computed in `get_ds` on the full 0D series BEFORE the per-study prep. Every other target shot is the training pool, and the `target_shot_order` case axis picks num_target_shots of it: `ascending` (the base extrapolation, lowest hazard first, no name token), `descending` (the highest-hazard pool shots, closest to the test regime) or `spanning` (each shot's footprint is 32 evenly spaced complete timeslices of the 7 power balance inputs plus energy_mhd_MJ, z-scored over the pool, shots differ by their exact Gaussian-kernel MMD with the median-heuristic width, 1 shot is the MMD medoid, 2+ start from the most different pair then go farthest-first, so picks are nested from 2 up, ~7 s for the ~710-shot MAST pool). An order only applies with target shots in training, so every order shares the hyperparam case and the stateless transfer twin, while the stat-normalization twin and the submodule / pseudo-model-type prereqs keep the case's order. Domain-adaptation cases reuse the test set for checkpoint selection (no separate val set, slightly optimistic but consistent).

### Config

- Field roles (`transport_study/config.py` module docstring): every Config field declares one with its type. `Identity[T]` (study_name, parent_study) names the study, its working dir and the study it borrows from. Unmarked fields are LOCKED (anything that changes what a case produces under an unchanged name: datasets, target, debug, max_ds_size, epochs, patience, sweep size, test set size and named test shots, dataset_fractions, num_result_checkpoints, every hyperparam_* field, transport's study-wide normalization and submodule variants), the default on purpose so a new field can never silently mix results. `Annotated[T, CaseAxis(<Case field>)]` marks a case-grid axis, free to change between runs. `Orchestration[T]` marks where and how jobs run (partitions, limits, wandb, working_dir_base), never locked. `fields_with_role`, `case_axes` and `differing_fields` read the markers.
- Study TOMLs mirror the roles: identity and locked fields at the top level, axes under `[cases]`, orchestration under `[orchestration]`, device paths and `target` under `[datasets]` (`PTPS_DATASET_PATHS` supplies default devices). A field outside its role's table raises naming the right one.
- Config lock (`orchestration/config_lock.py`, `config_lock.toml` in the working dir): identity + locked + case-axis fields and a final `[lock]` table (study_type, stamp, the parent's stamp), no orchestration fields, written atomically. Every Study init refuses a config whose identity or locked fields differ (naming them). Only `run_study` rewrites the recorded axes (`record_case_grid`), analysis jobs and plotting never do. A lock is only created over empty models/ and results/, so deleting one by hand cannot vouch for stale results, and clean_models / clean_results delete it. The lock reader takes the `[datasets]` paths alone (no env merge) and drops fields the class no longer has with a warning.
- `transport_study/config.py`: `StudyConfig` (Pydantic, frozen, global one-shot proxy `config`, `config.get_instance()` for the object itself), reads `PTPS_*` env vars. `debug` keeps every target shot but caps each source device at its `DEBUG_MAX_SOURCE_SHOTS` most recent shots (in `get_ds`), the epochs at `DEBUG_MAX_EPOCHS` (12), the validation interval at `DEBUG_EPOCHS_PER_VAL` (3), the sweeps at `DEBUG_HYPERPARAM_SWEEPS` (1 trial, and `launch_sweep` keeps at most that many agents running instead of `MIN_RUNNING_AGENTS`) and the averaged result checkpoints at `DEBUG_NUM_RESULT_CHECKPOINTS` (3, a CaseGridConfig validator). So a debug run validates 4 times, patience never fires, and the TOMLs keep their production values. `wandb_entity` (`PTPS_WANDB_ENTITY`) is required for sweeps, every sweep, agent and API read uses it
- CPU training (`Orchestration` fields under `[orchestration]`, hs1 sets them in every TOML): the `cpu_model_types` (no env var, checked against the study's `FIELD_CHOICES`, prereq pseudo types by their own name) may also train and sweep on `cpu_partition`, then the `cpu_fallback_partitions` (`PTPS_CPU_*`), with `cpu_train_cpus` per CPU job, `train_mem` the `--mem` of every training and agent job on both devices (a CPU job also holds the device arrays, hs1 uses 16G for power balance and 48G for profile and transport), and `cpu_capable_buffer_gpus` the idle primary GPUs a CPU-capable case leaves for the GPU-only cases of any study (it replaces `buffer_gpus` for them, so a negative `buffer_gpus` never queues them on a full GPU partition). Each pass (`Study._launch_ready_cases`) places the GPU-only cases first and the CPU-capable ones on the leftover primary GPUs, else the CPU partitions, one `pick_partition` per case passed down to `launch_train` / `launch_sweep`. The pending watchdog also cancels a CPU-capable case's job pending 30 min for a primary GPU and any job on a CPU fallback partition, and the stuck-job watchdog gives jobs on CPU partitions `CPU_WATCHDOG_SCALE` (4x) its thresholds. Checkpoints move between the devices exactly (orbax, x64, the restore template sets the device).
- `orchestration/study.py`: `CaseGridConfig(StudyConfig)` shared base for study configs (working_dir_base, training_datasets, domain_adaptation_methods, target_shot_orders, target_test_set_size or target_test_shots (exactly one), hyperparam_domain_adaptation, hyperparam_num_target_shots, dataset_fractions, num_result_checkpoints) and one validator checking every field named in the per-study `FIELD_CHOICES` ClassVar against its allowed values. Each study nests its own `Config(CaseGridConfig)` adding its case axes and study-specific hyperparam fields. Power balance and transport default to unfrozen submodules (freeze_submodules_options=(False,), hyperparam_freeze_submodules=False). `HYPERPARAM_TARGET_SHOTS` also lives in study.py
- `pyproject.toml`: dependencies, build (hatchling), tooling config. popsim, torax and transport-validation-datasets install editable from their submodules (`[tool.uv.sources]`), so a clone needs `git submodule update --init` before `uv sync`. TVD pins disruption-py 0.14.0, and `[tool.uv] override-dependencies` sets numpy to popsim's range over disruption-py's numpy<2 pin
- GPU group: `uv sync --group gpu` for JAX CUDA 13 support

### Data Schema

Every device store holds the shared schema of transport-validation-datasets (`store_schema.STORE_SIGNAL_ATTRS`, every signal with its unit and IMAS ref), IMAS names in SI units on `(shot, time_idx[, rho_tor_norm])` with `time` on `(shot, time_idx)`: `ip`, `b0`, `energy_mhd`, `beta_tor_norm`, `n_e_line_average`, `minor_radius`, `geometric_axis_r`, `elongation`, `triangularity_upper` / `_lower`, `power_ohm`, `power_radiated`, the heating powers `power_nbi` / `power_ic` / `power_lh` / `power_ec`, `r0` on `(shot,)` (the fixed major radius b0 is given at, as IMAS defines b0), the profiles `t_e` / `n_e` with `_error`, `_gradient`, and `_gradient_error` companions (GP or IDA 1-sigma uncertainties on every device), `fresh_profile`, and `fresh_equilibrium` (left out of the study stores, `STUDY_STORE_SIGNALS`). `get_ds` converts a store to the study's working units with `signals.convert_to_working_units`: any non-SI unit becomes a name suffix (`ip_MA`, `energy_mhd_MJ`, `n_e_line_average_1e20`, `power_ohm_MW`, `t_e_keV`, `n_e_1e20`, ...) the four heating powers sum to `power_additional_MW`, and `b_geo = b0 r0 / geometric_axis_r` is the vacuum field at the geometric axis, which every model uses (TORAX `B_0` at `R_major`, q_star, aB0, the H89 / H98 / P_LH scalings). Every store holds `beta_tor_norm` as IMAS defines it, `100 beta_tor a |b0| / |ip|[MA]` with `beta_tor = 2 mu0 <p> / b0^2` and b0 at r0, built on every device from the reconstruction's own stored energy and volume (TVD `generic.normalized_beta`), so the betan <-> pressure inversions (profile `Inputs.beta` / `te_approx` / `w_approx`, transport `beta_from_energy_mhd` / `beta_tor_norm_from_energy_mhd`) use `b0`, not `b_geo`, and the profile and transport studies carry `b0` alongside `b_geo`. Those inversions call TVD `generic.normalized_beta` / `energy_mhd_from_normalized_beta` (jit-safe, builtin abs) with popsim `calc_plasma_volume` as the volume, since no volume is stored: the round trip recovers the store's betan only up to volume_approx / V_recon (a few percent on C-Mod, ~10 percent on MAST), a known and accepted bias. Power balance inputs are `ip_MA`, `b_geo`, `geometric_axis_r`, `minor_radius`, `elongation`, `n_e_line_average_1e20`, `power_additional_MW`, with `energy_mhd_MJ` the target. The profile and transport preps interpolate the profiles onto the uniform 51-point `RHO_GRID` over `[0, 1]`, and the profile prep adds `t_e_shape` / `n_e_shape` (`PROFILE_SHAPE_VARS`, which the transport prep drops: its sciml profile submodule restores the shape basis fitted in its profile prereq case). The profile prep keeps only `fresh_profile == 1` slices, moved to the front of each shot's time axis in time order (`keep_fresh_timeslices`, the axis cut to the most fresh slices any shot holds, so time_idx counts a shot's fresh slices and the time coordinate keeps their times, about 98 percent of a DIII-D shot's slots are stale), the transport prep is the union of both studies' signals minus `beta_tor_norm`, keeps the forward-filled profile timeslices (contiguous segments matter more than freshness for rollouts, `fresh_profile` rides along as data). Every store is one contiguous 1 kHz segment per shot, so no prep reindexes time, `get_ds` only checks the step. `get_ds` keeps the `max_ds_size` most recent shots of each device, every shot by default (None), and returns the prepared dataset alone.

### Tests

`uv run pytest` runs the fast suite only: `addopts = -m 'not slow'` in pyproject. The `slow` marker covers anything that trains a model, runs a TORAX relaxation, renders comparison figures, or needs real device data (the live device tests now live in the TVD submodule's own suite). Run those with `-m slow` on a GPU node, one suite at a time - concurrent suites OOM the node GPU. Study tests also need the `PTPS_*` env vars from `.vscode/launch.json`, without them they fail with misleading shot-count errors.

On a node without a GPU (like the interactive node), the jax CUDA13 plugin's CUDA library version check hangs forever at the first JAX op, which `popsim.ml` runs at import, so collection never finishes and pytest prints nothing. The root `conftest.py` defaults `JAX_PLATFORMS=cpu` when no `/dev/nvidia*` device exists, which also covers VSCode test discovery. Any other entry point that imports JAX on such a node still needs `JAX_PLATFORMS=cpu` set by hand.

The sample device datasets (`cmod-low1/low2/high.nc`, `mast-low1/low2/high.nc`) are NOT in the repo (they were Git LFS files until September 2026). Tests that open them read them from the directory in `PTPS_TEST_SAMPLE_DIR` via `tests/sample_data.SAMPLE_DIR` and carry `requires_sample_data`, which skips them when the variable is unset. Tests that only need a loaded config use `path/to/...` placeholders, and study tests that only build configs use a `tmp_path` working dir so no stale `config_lock.toml` can trip them. Tests that need a real study over data use the session fixture `synthetic_device_stores` (two synthetic TVD stores, cmod and mast, 3 shots each, 30 to 50 steps long). Any path that builds dataloaders there needs `target_test_set_size` >= 2 (popsim rejects a single-shot whole-episode test set), and the time-dep studies' 100-step training segments must be shortened through the public `base_dataloader_config` hook.

Organization rules the suite follows:

- Tests mirror the package layout. Cross-study behavior is tested once in `tests/orchestration/`, not once per study: `test_study_config.py` (config lock, sectioned TOML, parametrized over all three studies), `test_sweep_configs.py` (every sweep yaml of every study, driven off `Case.VALID_MODEL_TYPES`), `test_tables.py` (the generic comparison-table writer), `test_stages.py` (stage segmentation), `test_target_shots.py` (the test cutoff and the three target shot orders, plus a slow test rendering the target_shot_orders figures with each PTPS_DATASET_PATHS store as the target, into PTPS_TEST_WORKING_DIR_BASE/target_shot_orders). Per-study files cover only what actually differs - case naming, the case grid, per-study table specs and plotting. Architecture-level module behavior lives under `tests/modules/<family>/`: `tests/modules/transport_predictor/test_transport_module.py` covers env state seeding, trainable selections, the transformer history buffer, and the TORAX P_aux / absorption wiring, while `tests/transport_transfer/` keeps only study-level wiring.
- Never let a test reach into an underscore-prefixed production name. When coverage needs an internal, the fix is to make the symbol public (that is why `case_coords`, `replace`, `kill_stuck_jobs`, `make_weighted_device_weights`, `shot_stages`, `transfer_lr_scale`, `nn_coefficients`, `build_provider_and_geo` and `transport_coefficients` carry no underscore) or to drive it through its public caller (`_summarize_case_errors` via `collect_results`, `_kill_long_pending_jobs` via `run_unfinished_cases`).
- Orchestration tests drive `StubStudy`/`StubCase` from `tests/stubs.py` via the `make_stub_study` fixture rather than building a real case grid. `stubs.mark_analysis_done` stands in for a finished analysis job, and `StubCase(hyperparam=True)` also owns sweep agent jobs.
- `tests/modules/profile_predictor/conftest.py` provides `make_torax_module` and `sample_timeslices`, and TORAX-backed tests must use them instead of re-deriving module kwargs (the sample files predate `ds_source_idx`, which the fixture fills in). Tests using `sample_timeslices` must carry `requires_sample_data`.
- Test modules never import an underscore-prefixed name from the package. When a test needs to reach production internals, either the symbol is public or the test goes through the public path.
- No docstring-only stub tests remain (2026-10-04). A test either pins real behavior or is not written.
